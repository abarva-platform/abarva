## Plain-English Summary

The d09 RFP Pack was generated by a single 128k-token Claude call that took 8-9 minutes end-to-end. The monolithic call was the root cause of two problems: (1) wall-clock time made the first-event experience feel broken, and (2) any quality-gate rewrite had to regenerate the entire document even when only one section failed.

This PR introduces a parallel map-reduce generator for d09. Instead of one large call:

1. **10 parallel section calls** (§2-§11) run concurrently — each writes one self-contained heading + table + prose block. Each call targets ~4k tokens and completes in 15-30 seconds. Wall-clock for all 10 in parallel: ~30 seconds.
2. **Assembly pass** generates §1 (executive summary + decision table) after seeing all other sections, then stitches the document in canonical order.
3. **Quality gate** runs as before on the assembled body — and targeted rewrites can now be scoped per-section rather than regenerating the full document.

Expected wall-clock: ~2-3 minutes vs. 8-9 minutes previously.

The feature is **flag-gated**: set `ABARVA_SOURCE_D09_MAP_REDUCE=1` in ACA env to enable. The existing monolithic path remains the default until the parallel path is live-proven on the pilot event.

## Known Gaps

- §1 assembly pass sees all sections, but if multiple sections failed the exec summary will reflect placeholder content — acceptable for a first-event pilot proof, not for live client delivery
- Targeted section rewrite (regenerate only the section that failed quality gate) is not yet wired — the existing quality-gate rewrite still regenerates the full document. Follow-on: scope the rewrite prompt to the failing section only.
- `tokensIn` is not summed across parallel calls in this implementation (set to null). This is a metrics gap, not a functional one.
