## Plain-English Summary

A one-line correction to the committed test-CI coverage census. The same
mechanism a previous correction documented has recurred, so this record exists
mainly to say that the earlier fix corrected the numbers and did not close the
hole.

Four changes landed on `main` in close succession. Each added test files and each
regenerated the census against its own base. When two of them arrive at the
**same** committed counts, git has nothing to reconcile: the merges are clean, no
conflict is raised, every pull request reports mergeable, and the last one
squashed onto `main` carries a number describing **its own** base rather than the
tree that resulted.

The merged tree holds one more test file than the committed census describes:
`testFiles` 2879 where the tree regenerates to 2880, and `coveredTestFiles` and
`pullRequestCoveredTestFiles` 2715 where the tree regenerates to 2716.
`uncoveredTestFiles`, `directoriesWithTests`, `directoriesFullyCovered` and the
per-directory breakdown were already correct — only the three file totals were
affected, because every addition landed in a directory that was already counted.

This change regenerates both censuses against the current tree. Nothing else is
touched.

Two things are worth recording beyond the numbers.

**A clean merge of a generated file is still not evidence that the file is
right.** That was the lesson of the previous correction and it held here
unchanged: nothing in the pull-request signal distinguished this case from a
correct one.

**The generator's own success line is circular.** `audit:test-ci-coverage:write`
prints `census drift: committed census matches this run` _after_ writing, so it
reports agreement with the file it just rewrote. It printed exactly that on the
drifted tree. The non-circular check is `git status` after the regen: a modified
census file is the drift. Any future reader of this script should judge it by the
working-tree diff, not by that line.

## Known Gaps

- **The hole is still open, and this is now the second occurrence.** Nothing
  detects the identical-counts case at merge time; it surfaces on the next
  change. Closing it means treating this file as generated rather than committed
  — regenerating it in CI and asserting rather than storing it — which is a
  larger change than a numeric correction and is not attempted here. Until then,
  the drift recurs whenever two pull requests adding equal numbers of test files
  land close together, which on this repository's current cadence is often.
- **The generator's agreement line remains misleading.** This record documents
  it; the script is unchanged. A reader who trusts that line will conclude a
  drifted tree is clean, which is exactly what happened before the `git status`
  check was run.
- **Only the totals were wrong again.** The per-directory breakdown was
  unaffected because every addition landed in an already-counted directory. A
  collision in a directory one side creates would also skew
  `directoriesWithTests`, and nothing here makes that case easier to see.
