## Plain-English Summary

This PR builds the deterministic calculation engine at the heart of the
Nexus Pricing Engine: given a Move's archetype and a small set of
scope-driver quantities (integration count, impacted-user count, rollout
waves, etc.), it computes role-by-role hours, resolves an hourly rate for
each role, and produces a fully-provenanced cost estimate — low/expected/high
— with every line traceable back to the scope driver, effort rule, model
version, role mix, and rate line that produced it. No UI, no API route, and
no live database are part of this PR (see `docs/architecture/
PRICING_ENGINE_CURRENT_STATE.md` §14 for the direction decision this build
follows) — everything here is proven with local unit/golden tests, the same
posture PR1-PR3 took.

Concretely, this PR adds:

- **A third migration**

  8 tables PR2 explicitly deferred: `pricing_archetypes`,
  `pricing_activity_packs`, `pricing_effort_drivers`, `pricing_effort_rules`,
  `pricing_activity_role_mix`, `pricing_archetype_activity_map`,
  `pricing_range_policies`, `pricing_agent_costs`. Every table follows PR2's

## Honesty Disclosure — Hand-Authored Content

Every row in every one of the 8 new CSVs is hand-authored planning-estimation
content — general enterprise IT delivery/consulting domain knowledge (which
activities a program of this archetype needs, roughly how many base hours
and driver-unit-hours each takes, roughly who staffs it), **not** a
researched market benchmark and **not** extracted from any source workbook.
Every row is tagged `source_artifact = "hand-authored-pr4"`, matching PR1's
own precedent (`hand-authored-pr1`) for its 8 hand-authored capabilities and
9 hand-authored roles. This is explicit, directional V1 content whose whole
purpose is to make the engine's math deterministic, explainable, and
versioned — it is **not** claimed to be precisely accurate on day one, and is
expected to be tuned against real delivery data (actuals from completed
Moves) over time. This matches the brief's own framing quoted in the
execution prompt: "deterministic, explainable, versioned" does not mean
"precisely accurate first try." See `manifest.json`'s
`pr4_effort_engine_pack.honesty_disclosure` for the same statement recorded
alongside the data itself.

Two `pricing_archetype_activity_map` exclusions are similarly disclosed, not
silently omitted: `AP-SHARED-11` (Vendor/Commercial/Supplier Governance) and
`AP-SHARED-06` (Hypercare) are both marked `excluded` for `ARCH-05` (Process
& operating-model transformation), on the documented judgment that a purely
internal operating-model/process initiative by default has neither a
third-party sourcing relationship nor a technical go-live cutover event. Both
are one row away from being included if a real Move's scope says otherwise.

## Decimal / Currency Representation

PR0's audit found no decimal/fixed-point money library anywhere in this repo
and no such dependency in `package.json` (`docs/architecture/
PRICING_ENGINE_CURRENT_STATE.md` §6) — every existing cost calculation
(expert-kernel, workforce-economics) uses plain JS `number` (float) with
display-time rounding only. This engine adopts **integer cents** as its
internal money representation for all new calculations (`src/lib/pricing/
effort-engine/money.ts`): every cost value is a whole number of US-cent
units, rounded exactly once (Math.round) at the single point a fractional
value could arise — `hours × hourlyRateCents` — and never again; summing
already-integer cents (module totals, archetype totals, portfolio roll-ups)
is exact integer addition with no further rounding. Conversion to a display
dollar amount happens only at output boundaries
(`centsToDisplayDollars`). Hours themselves stay plain floats, rounded to 4
decimal places (`roundHours`) at each defined pipeline step and once more at
the final total, purely so the numbers a human reviews in the provenance
drilldown are clean — not because JS float arithmetic is non-deterministic
(it is fully deterministic for a fixed operation sequence, which is what the
determinism proof below actually tests). This deliberately diverges from the
rest of the repo's float-money convention; no new npm dependency was added
(`package.json` was checked first, per the brief).

## Known Gaps

- **No live ACA/Azure Postgres proof.** Every test runs against an injected
  in-memory fake store (`pack-loader.test.ts`), a hand-built or real-CSV-
  parsed in-memory snapshot (everything else), or the real committed CSV
  files read directly off disk — never a live database connection (none is
  available in this environment), matching PR2/PR3's own stated limitation.
- **Range-policy inputs are mostly caller-supplied judgment, not yet
  derived from live signals.** Of the five range-policy dimensions, only
  rate-card coverage is derived from a real, computed source (designed to
  take PR3's `coverage-report.ts` output directly). Scope maturity, evidence
  quality, delivery novelty, and quantity uncertainty are supplied by the
  caller today — a documented gap for a future PR to close by deriving them
  from real Move-context signals.
- **`snapshot-service.ts` and any `context-projection.ts`-equivalent are
  intentionally NOT implemented** — per the execution prompt's explicit
