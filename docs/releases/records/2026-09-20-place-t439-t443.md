## Why all five belong in the same track

The track's own stated purpose is *audit and gate integrity — advances no
lifecycle stage*, and each of the five is that:

- one is deployment/acceptance bookkeeping;
- three concern unreached test directories drawn from the coverage census;
- one is a security audit of the application-side tenant boundary on Source
  events.

The last was the only one worth pausing on. It concerns Source, so the
lifecycle stages were the tempting home, but it **audits a fence rather than
building a capability** — it advances no stage, which is the track's own test.
Placing it on a lifecycle stage would have made the vision-completion figure
read as if Source had moved when it had not.

## The treadmill this is the fourth instance of

The unmapped-id gate has now blocked the board four times today, each time
within minutes of a filing batch. That is the gate working — an unmapped id is
invisible to the queue rather than merely unranked — but it is worth naming the
pattern rather than quietly paying it again.

The cost of the current design is that **five unclassified rows make the whole
board unavailable**, turning partial information into none. A holding bucket
would keep the board generating while still showing the items as unplaced.

**That change is not made here**, for two reasons. The blocking behaviour is
what produces the prompt placement this repository has actually been getting —
four batches placed the same day they were filed — and weakening a gate because
it keeps firing is the reasoning that should be hardest to accept from whoever
built it. It is recorded as a question for whoever owns the queue, not resolved
by the agent it inconveniences.
