# 2026-10-04-moves-capture-composition — Moves: capture composition polish (flag OFF)

## Release ID

`2026-10-04-moves-capture-composition`

## Status

`candidate`

## Plain-English Summary

The redesigned phase capture was mounted inside the existing phase workspace
without re-reading the page it landed on. The result says two things twice.

The capture flow opens with its own phase strip — all six phases, the current
one marked, each with how many of its inputs are answered — and under it a
three-step bar naming the step a person is on. Directly **above** that, the
workspace still renders the legacy stage head: the phase title as an `h1`, the
phase question, the phase lede, an `AVA · MOVES` chip, and a progress card
repeating the answered count the phase strip just gave. A person reading down
the page meets the phase name three times before reaching the first question.

Separately, the workspace surface tabs (Work / Files & Evidence / Phase
Intelligence / Cost & Effort) sit **above** the whole agent dock, so the control
that switches the workspace column is outside the column it switches. The dock
has always taken a `tabs` slot in its workspace for exactly this; the host had
simply never filled it.

This increment is composition only:

- The **same** tab row node is handed to the dock instead of rendered above it,
  so it sits with the content it switches. It is rendered once either way.
- The stage head stops repeating what the capture flow already states — title,
  question, lede, aVa chip, progress card. It keeps what the flow does **not**
  state: the blocked-phase notice and the readiness-workbook actions. Left with
  neither, it collapses rather than leaving an empty band.

No capture field, key, help text, structured editor, save, gate, or evidence
behaviour changes. Nothing is removed from the page that is not stated
elsewhere on the same screen.

Everything is behind `moves_capture_composition_v1`, **off for every tenant**,
and resolved server-side as a conjunction with `moves_capture_v2` — the polish
has nothing to show where the redesigned capture is not what renders.

No client receives this change: it is gated by a feature flag that is off for
all clients. `includeTenants: []` — `moves_capture_composition_v1` resolves off
for every tenant, including the synthetic demo tenant currently enabled on
`moves_capture_v2` and `moves_home_v2`. With the flag off the phase workspace
renders byte-for-byte as it does today.

## Known Gaps

- **No signed-in proof, and none is claimable.** With the flag off for every
  tenant the polish renders nowhere, so this record claims `merged`, not
  `live-proven`. A signed-in walk of a phase with the flag on — confirm the tab
  row switches surfaces from inside the dock, that the phase is still named
  once and legibly, and that a blocked-phase notice and the workbook actions
  still appear — is owed as the gate on enabling the first tenant.
- **Measured at one width only.** The compact head is asserted in jsdom, which
  does not lay out. The narrow-viewport rules for the full head already exist;
  the compact variant collapses to one column by construction, but has not been
  rendered and measured at phone width. Owed with the signed-in walk.
- **The crumb still names the phase.** `Move / P1 · Charter` above the head
  repeats the phase strip's label. It was kept because it is also the way back
  to the move, which the strip is not. A separate decision, not this slice.
- **P0 is covered but not separately pinned.** This rebased onto the P0 mount
  (`moves_capture_p0_v1`), so `captureFlowMounted` is now the disjunction of
  the phase-1–5 mount and the P0 arm, and the polish follows P0 for free — that
  is the point of naming the condition once. The four new cases exercise P1
  only; a P0 composition case is worth adding when a tenant is first enabled on
  all three flags together.
- The other half of the deferred capture polish — paste-client-notes →
  governed fill-from-notes in the dock — is a separate change and not included
  here.
