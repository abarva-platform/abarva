# 2026-09-27-u545-terminal-stage-fact-derived-beats — Terminal Source stage intake beats derived from event facts

## Release ID

`2026-09-27-u545-terminal-stage-fact-derived-beats`

## Status

`candidate`

## Plain-English Summary

The final stage of a Source event asks the user to confirm the value the event has actually
realized. Until this change the checklist on that stage, and the three tick-boxes on its approval
gate, were **example content** copied from a stage template — the same words for every event, every
client and every category — while the value chart above them was computed from the event's own
facts. A reader had no way to tell the two apart, and the model that answers questions about the
stage was handed the example content introduced as authoritative.

This change derives that stage's checklist and gate boxes from the event itself: the value levers
its resolved category declares, the target range computed from its own committed facts, and the
per-lever realized-to-date figures already read from the data plane for this stage.

The distinction the change is careful about is the difference between **not measured** and
**measured at nothing**:

- No realization record has been read at all → the stage asks for the actuals and says plainly that
  nothing has been read. It never reports a zero.
- A realization record has been read and no lever has realized yet → that is a real, reportable
  zero for the total, and it is shown as one.
- Some levers have realized → each of those carries its own figure; **every other declared lever is
  shown as "not yet realized", per lever and by name, never as $0 and never as a guess.**

The gate's approver, the fact that this stage approves nothing onward, and the sentence describing
its completion review are **read from the existing terminal-gate contract**, not phrased a second
time at the surface.

## Layer Impact

Release lane: **`global-control-lane`** — shared Source product behaviour for all clients, no feature
gate added.

- **Layer 3 → Layer 4 projection (Source product):** a stage view's two intake beats stop being
  template content and become a projection of the event's canonical facts and resolved archetype.
  No new data is read and no schema changes.
- **Layer 2 / data plane:** none. The per-lever realized-value signal was already read at the live
  call site and passed to the step-insight builder; it is now also passed to the stage-view builder.
- **Model prompt:** the grounding block's "scaffold content" disclosure now correctly comes off this
  stage, because the content it warns about is gone.

**Two defects in this change were found by the existing provenance harness, not by review, and are
recorded because the second one is the more interesting:**

1. The un-observed branch's gate boxes were static prose. The harness classified `gate.confirms` as
   `derived_from_neither` — its verdict for content that differs from the template and follows
   neither the facts nor the archetype, which is the shape of a hand-written replacement for a
   fixture. The branch now states the event's declared lever count and its computed target range,
   both of which are real whether or not anything has realized.
2. The un-observed beat built its per-lever rows and **never returned them** — the object literal
   simply did not mention the local. Nothing else noticed: the value was assigned, so no lint rule
   fired, and the beat still rendered. The harness saw it as `tasks` moving with the archetype but
   not with the facts, which is precisely what a beat that names the levers and drops their numbers
   looks like.

**One assertion in the new suite was wrong and was corrected, with the reason stated in the file.**
It forbade `$0` anywhere on the gate in the *measured-and-empty* state. That is wrong: once
realization has been measured, `$0 realized to date` is a real reportable zero, and the sibling
stage already established that reading. The rule the item states is about a **lever**, so the
negative now sits on the per-lever beats and the aggregate carries an exact anchored positive.

**A guard this change retires, handled deliberately rather than deleted.** Three cases across the
two provenance suites asserted a conjunction: a stage that *still carries* template beats **and**
whose template approver reads as a person's name. The terminal stage was the last member of that
intersection, so deriving it empties the set — and each case used `.find(...)!`, which would have
handed `undefined` to the lookup and silently re-pointed the case at another stage. The two
properties are now asserted over their own non-empty populations (and widened from one sampled stage
to the whole armed set), and **the emptiness of the intersection is itself asserted**, so a future
stage arriving carried-and-person-named fails and forces the conjunction case to be reinstated
rather than inherited as silence.

**A provenance verdict this change splits.** The parameterised case asserting every derived stage's
`gate.approver` is `archetype_derived` was correct only while every derived stage had an archetype to
read a deciding role from. On the terminal stage the deciding role is fixed by the terminal contract
— a policy, not a property of this event's archetype — so it is `policy_derived` and provably does
not move with the archetype. Asserting otherwise would have been an over-claim of the same kind an
earlier item corrected.

**Mutations.** Recorded in the pull request, each verified to have changed behaviour before its
suite was run, including the direction the item names by name: reinstating the template's
confirmation labels must go red naming the stage.

**Per-field, not aggregate.** The regenerated provenance artifact records the terminal stage as
`tasks: fact_derived`, `gate.confirms: fact_derived`, `gate.generates: derived_empty`,
`gate.approver: policy_derived`, `declared.tasks/gate: fact_derived`, `scaffoldSource: null`, with
`movesWithFacts` and `movesWithArchetype` true for both intake beats.

**Toolchain.** `NODE_OPTIONS=--max-old-space-size=6144 npx tsc --noEmit --pretty false` with
`tsconfig.tsbuildinfo` removed first: **exit 0**, judged by exit code. `npx eslint` over the six
changed files: **exit 0**.

**Not done, and not claimed.** No signed-in run. This change alters what a stage view contains, and
reading it on a live tenant is a separate proof lane; nothing here is described as live-proven.

## Known Gaps

- **No signed-in proof.** The stage's rendered checklist and gate boxes have not been read on a live
  tenant in this release. State is `merged`/`deployed`, never `live-proven`.
- **`purpose` is still template content on this stage,** as it is on all ten. The per-beat provenance
  declaration covers the two intake beats only, and the per-field artifact is where the remaining
  carriage stays visible. Deliberately out of scope here.
- **Four stages still carry template beats** — scope, pricing, executive_decision, transition — and
  none of the four has a dedicated tenant-scoped per-lever fact signal read at the live call site,
  which is the narrowing an earlier item recorded. Deriving them needs a signal first, not a
  derivation first.
- **A fourth copy of four small formatters.** `usd`, `idSegment`, `citedDocFor` and
  `targetBandFor`/`targetLabel` now exist privately in four sibling modules. The extraction touches
  three modules this change does not own, so it is filed as its own item rather than folded in.
- **The un-observed branch is the one the provenance harness measures,** because that harness builds
  this stage with no realized signal. The observed branches are covered by the new behavioural suite
  instead, not by the artifact.
