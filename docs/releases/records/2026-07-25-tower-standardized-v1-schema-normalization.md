# 2026-07-25-tower-standardized-v1-schema-normalization — Normalize F05/F11/T09/T10 to one canonical schema across all 5 tenants

## Release ID

`2026-07-25-tower-standardized-v1-schema-normalization`

## Status

`candidate`

## Plain-English Summary

Before running the Enterprise Book paid generation for first-capital and meridian-health, a
zero-cost dry run crashed: `loadTenantEvidenceIndex()` assumed every tenant's
`T10_evidence-items.csv` used skyharbor-air's column names. It doesn't. Auditing all four
schema-dependent governed files (`F05_applications-systems.csv`, `F11_vendors-contracts-licenses.csv`,
`T09_risk-governance.csv`, `T10_evidence-items.csv`) found skyharbor-air uses a different column
schema than the other 4 tenants for F05/T09/T10, and `apex-retail` uses a third, F11-specific
schema — real, structural inconsistency in the governed `tower-standardized-v1` package itself, not
a bug in any one consumer. No documented canonical schema exists for these four files (confirmed:
`SCHEMA_DIFF.md`/`SCHEMA_DIFF.csv` explicitly mark them `snake_case_lineage_copy`, i.e.
pass-through, unlike `T01`/`F12`/etc., which do have a real harmonized `Transform`).

Rather than adding permanent per-tenant schema-branching code — which every future consumer would
also need to carry — this release normalizes the source CSVs themselves to one canonical column
schema per file, chosen as the real 4-of-5-tenant majority (F05/T09/T10) or, for F11, the
3-of-5-tenant majority with apex-retail's and skyharbor-air's distinct fields preserved as
additional named columns. Every real value is preserved: renamed under its new canonical column
where the concept is genuinely equivalent, or kept under an explicit `legacy_*`/tenant-specific
extra column where no clean equivalent exists. Nothing was discarded and nothing was fabricated —
verified by row-count parity (2,745 real values changed position, zero rows lost, across all 20
files) and spot-checked value-by-value against `git show HEAD:...` for the pre-normalization
originals.

Two consumers besides `build-home-knowledge-v4-review-pack.mjs` were found and updated in lockstep:
`reconcile-tenant-applications.mjs` had its own independent legacy-schema detection, now removed
(single schema, F19 ownership-join fallback applied per row rather than per tenant, since the join
file exists for every tenant). A third file, `project-lakeshore-v7-to-tower-standardized.mjs`, was
found to be a **producer** with its own already-stale hardcoded headers for the same two files — a
real landmine that would silently re-corrupt the normalization if ever re-run — flagged with an
explicit staleness warning rather than silently left dangerous or spuriously "fixed" without
understanding its actual (different, richer, holdco-hierarchy) intended purpose.

## Changes Included

- `tower-standardized-v1/<tenant>/family-2-technology-estate/F05_applications-systems.csv` (all 5
  tenants): canonical columns `application_id, application_name, domain, primary_business_owner,
  technical_owner_team, platform_type, hosting_model, environment, criticality,
  annual_run_cost_usd, users_or_entities_supported, integration_count, data_classification,
  modernization_state, evidence_id, legacy_platform_category, legacy_vendor, source_file,
  source_row, value_source`. skyharbor-air's real `category`/`vendor` values preserved under the
  two `legacy_*` columns (no majority-schema equivalent); `business_function`→`domain`,
  `deployment`→`hosting_model`, `lifecycle_stage`→`modernization_state`,
  `run_cost_fy26_usd`→`annual_run_cost_usd`, `primary_dataclass`→`data_classification` renamed
  (concept match; value vocabularies are NOT force-harmonized across tenants -- see Known Gaps).
- `tower-standardized-v1/<tenant>/family-4-financial-commercial/F11_vendors-contracts-licenses.csv`
  (all 5 tenants): canonical columns `vendor_id, vendor_name, category, owned_by, business_owner,
  technology_owner, annual_contract_value_usd, renewal_date, criticality, license_or_unit_basis,
  commercial_risk, renewal_risk_rating, evidence_id, legacy_notes, source_file, source_row,
  value_source`. apex-retail's `renewal_risk` (a severity scale: high/medium/low) kept as its own
  `renewal_risk_rating` column, deliberately NOT merged into the majority schema's `commercial_risk`
  (a free-text risk description: "concentration risk", "price escalation", etc.) -- confirmed by
  inspecting real values that these are different business concepts, not just different names for
  the same fact.
- `tower-standardized-v1/<tenant>/ai-control-tower/T09_risk-governance.csv` (all 5 tenants):
  canonical columns `initiative_id, risk_id, risk_domain, severity, control_status,
  exception_or_gap, owner_role, legacy_mitigation, legacy_evidence_id, source_file, source_row,
  value_source`.
- `tower-standardized-v1/<tenant>/ai-control-tower/T10_evidence-items.csv` (all 5 tenants):
  canonical columns `evidence_item_id, initiative_id, source_document, source_locator,
  source_timestamp, review_state, confidence, legacy_source_type, legacy_claim_supported,
  legacy_freshness_status, legacy_trust_status, source_file, source_row, value_source`. Also fixes
  a real duplicate-header bug already present in the majority schema's own files (`source_file`
  appeared twice -- once as the actual source document, once as governed lineage metadata) by
  disambiguating the content column to `source_document`.
- `scripts/knowledge/build-home-knowledge-v4-review-pack.mjs`:
  - `loadTenantDatasetRegistry()`: removed `TENANT_SCHEMA_FAMILY` branching, single canonical
    `available_dimensions`/`available_measures` per dataset now.
  - `loadTenantEvidenceIndex()`: reads canonical T10 columns; falls back to `legacy_*` columns
    per-row (not per-tenant) for rows normalized from the old skyharbor-air schema.
    `LOW_SPECIFICITY_LOCATOR_PATTERN` extended to also catch the majority schema's own generic
    `"section N.N"` locators, not just skyharbor's `"synthetic locator N"`.
  - `loadTenantApplicationOwnershipFacts()`: legacy-schema detection removed; F19 ownership-join
    fallback now applied per row whenever `primary_business_owner` is blank, for any tenant (the
    join file exists for all 5, not just skyharbor-air).
  - `VISUAL_RENDER_RULES`: updated to the new canonical dimension/measure names. **Caught a real
    bug this same change would otherwise have shipped**: this block still referenced
    skyharbor-air's pre-normalization column names (`business_function`, `risk_type`,
    `trust_status`, `scope`, `annual_run_rate_usd`) after `loadTenantDatasetRegistry` had already
    been updated -- the zero-cost `unknown_visual_field` validator check caught the mismatch
    immediately on the first post-normalization preflight run, before any paid call.
- `scripts/knowledge/reconcile-tenant-applications.mjs`: removed its own independent
  legacy-schema detection (duplicate logic from the file above); F19 fallback now per-row.
- `scripts/lakeshore/project-lakeshore-v7-to-tower-standardized.mjs`: added an explicit staleness
  warning at the top of the file (its hardcoded `f05Headers`/`f11Headers` predate and diverge from
  both the pre- and post-normalization live schemas; re-running it as-is would silently
  reintroduce a fourth, incompatible schema for lakeshore-industries).
- `src/app/(maestro)/home/v4-preview/_fixtures/skyharbor-air.json`: regenerated by
  `reconcile-tenant-applications.mjs` -- ownership figures now correctly reflect the per-row F19
  fallback (682/900 applications with a real owner, previously computed from the same underlying
  join but via now-removed tenant-level branching).

## Known Gaps

- Column NAMES are now unified; VALUE VOCABULARIES are deliberately NOT force-harmonized across
  tenants (e.g. skyharbor-air's `modernization_state` column carries its own original lifecycle
  values -- "EOL Approaching", "Unsupported" -- which differ from the majority schema's
  vocabulary -- "retire_candidate", "optimize"). This was a deliberate scope decision: forcing a
  value-level crosswalk risks misrepresenting a real business judgment (e.g. asserting "EOL
  Approaching" categorically equals "retire_candidate") that wasn't actually made by whoever
  captured the source data. A future, separate effort could define a real value-taxonomy
  crosswalk if downstream consumers need cross-tenant value comparability, not just structural
  consistency.
- `apex-retail`'s and `lakeshore-industries`' book-mode fixtures don't exist yet (only
  skyharbor-air's does), so their renderer-proof step is skipped in `--preflight` output (structural
  preflight still passes cleanly for all tenants tested).
- `project-lakeshore-v7-to-tower-standardized.mjs`'s actual intended holdco-hierarchy schema (with
  `entity_id`/`parent_entity_id`/`portfolio_company_id` etc.) was not reconciled with or adopted
  into the canonical schema -- flagged as stale/dangerous, not redesigned. Whether that richer
  shape should eventually become the canonical one (for lakeshore-industries specifically, given
  its real holdco structure) is a real open question for whoever owns that projection, not decided
  here.
- The DB-backed consumers (`src/lib/tower/tower-semantic-projection.ts`,
  `tower-budget-rollups.ts`) were not touched -- they read from a Postgres table via generic
  multi-candidate field-name fallback lists, and the audit that found them could not locate the
  actual CSV-to-Postgres ingestion loader to confirm whether it's fed by `tower-standardized-v1`
  today. This is a disclosed, unresolved thread, not verified either way.
