# 2026-09-27-programs-attachment-directory-wiring — Wire the Programs attachment test directory into CI

## Release ID

`2026-09-27-programs-attachment-directory-wiring`

## Status

`candidate`

## Plain-English Summary

Four test suites that check how file attachments are handled inside Programs ran
on nobody's machine but a developer's. They were in the repository, they passed,
and no continuous-integration job executed them — so if a future change had
broken attachment uploads, text extraction, or MIME handling, nothing in the
build would have said so.

This change puts that directory into a job that runs on every pull request, and
it lowers the recorded count of directories still in that state from 17 to 16.
That count is a measurement, not a target: lowering it in the same change is
what keeps it honest, and raising it would be the edit to refuse.

The four suites were measured **before** they were wired, each executed on its
own: all four pass, 65 cases in total. So this buys the future rather than
repairing a break — which is the weaker of the two claims a wiring change can
make, and the only one available when the suites are already green. The
directory is not coverage of nothing: 19 files outside it use these modules,
including three attachment API route handlers, the artifact upload and
client-approval routes, the deliverable sign-off route, and five components.

**Source-text scanner judgement, per suite.** Negative for all four: not one

**Failing test first, then the fix — same scope both times.** Test edits alone,
with no workflow step: **3 failing of 14** in
`programs-unit-directory-ci-coverage.test.ts` — the census-resolution case, the
literal-naming case, and the ratchet count. With the step and the two
measurements updated: **0 failing of 18** across that suite and its sibling
`product-directory-ci-coverage.test.ts`.

**Three deliberate mutations, each verified to change behavior and each traced to
the guard that fired:**

1. Workflow step deleted → **4 failing**: the ratchet suite's three cases plus
   the baseline drift case.
2. Trailing slash added to the jest path — `…/__tests__/` — → the runner still
   executes all 4 suites and 65 cases **green**, and the gates still report
   **4 failing**. This reproduces the trap the predecessor item recorded: a
   command that runs the suites while the visibility gate reports every one of
   them as owned by no workflow. The measurement, not the command's own output,
   is what catches it.
3. Wiring kept, the baseline line restored → **exactly 1 failing**, the drift
   case alone, with the ratchet suite green. So the two edits are not redundant:
   each is held by a different guard and neither covers for the other.

**Full suite, clean baseline in a separate worktree — not a stash:** at
`91c4731b3de60f365146549f95f51a1bc0dea9e6`, `npm run test:behaviors` reported
**152 suites / 1658 tests / 0 failing**. On this branch: **152 suites / 1661
tests / 0 failing**. The three extra cases are the new `it.each` rows for the
wired directory. **0 failing before, 0 after**, and every census-reading gate in
that directory is inside that scope.
