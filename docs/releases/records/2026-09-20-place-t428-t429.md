## Plain-English Summary

Two newly filed backlog items were not in the structure map, so the execution
queue could offer neither and the board run failed. They are placed now, in the
platform-integrity track alongside the rest of their band.

This is the **third** batch the unmapped-id gate has caught on the first board
run after filing, which is the whole reason it exists: an unmapped id is
invisible to the queue rather than merely unranked.

## What the two are

One is deployment bookkeeping — ten merges sitting at `merged` whose deploy
proof already existed and was simply unrecorded. It was **already closed by
another agent** before this placement, which does not make the placement
redundant: the gate fails on an unmapped id whether the item is open or closed,
because the map declares structure rather than status.

The other is open and substantial: whether vendor-facing artifact routes
actually enforce a completed human approval before a render or export. It is
one of only two `consequential` rows left deferred in the control catalog, and
it carries an explicit instruction not to treat an output watermark as
equivalent to a decision gate. It is placed, not triaged — nothing here says
whether its premise holds.

### The toolchain suite was nearly mis-reported

Run as `node --test`, the queue suite reports **one** test. Run the way the
workflow runs it — `node scripts/exec/build-execution-queue.test.mjs` — it
reports **29 passed**. The file is a self-running harness, not a `node:test`
module, so the wrong runner silently collapses it to a single case and would
have been quoted here as evidence.

The number in the table is from the command CI actually uses.

### Why no new test

Asserting that these two ids in particular are mapped would restate the gate
against a snapshot and need editing every time an id is filed — the
hand-maintained-list shape this repository keeps removing. The gate is the
test, and it has now demonstrated itself three times.
