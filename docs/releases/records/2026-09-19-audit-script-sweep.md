# 2026-09-19-audit-script-sweep — Run the unclassified audit scripts and record what happened

## Release ID

`2026-09-19-audit-script-sweep`

## Status

`reverted`

## Plain-English Summary

**This release was reverted by `2026-09-19-unbounded-audit-sweep-revert`.** The
measurement published fixture-specific repository details, and the execution
boundary could not account for transitive writes outside tracked paths. The
remaining content records the original release claim for audit history; the
instrument and generated measurement are no longer present on the current
branch.

The repository has 185 npm scripts named `audit:`, `validate:` or `check:` that
no workflow runs and nobody has classified. Six of them had ever been executed
against `main`, and four of those six failed — so the number of checks that are
failing where nobody can see was known to be at least four and unknown above
that. Every decision about what to do with the other 185 has been taken from
their names.

This adds a sweep that runs them and writes down what each one did, and records
the first measurement. It is not a gate: it always exits 0, it changes no
classification, and it decides nothing. It produces the number the
classification work needs.

**The number: 58 of the 185 fail.** Not four. A further 11 exit non-zero only
because the environment is empty (no connection string, no model key) and 2
because they were never given the arguments they require; those are not defects
and are counted separately. 114 exit 0.

**The second number is the more useful one: 89 of the 185 write files into the
repository, and 72 of those exit 0 while doing it.** Half of this "audit" backlog
is not auditing anything. It is generating reports, and 66 of the 185 entry
points are named `build-*` or `promote-*`. That is a classification answer
arrived at by observation rather than by reading names, and it is what the
classification backlog was missing.

## QA / Validation

**The defect the instrument had first, measured rather than reasoned about.** The
obvious safe way to sweep is to read each entry file, skip anything containing
`writeFileSync`, and run the rest. That was built first and it is wrong in the
dangerous direction: **of the first ten scripts it cleared as read-only, four
wrote fifteen tracked files** under `reports/`. They write through an imported
helper, so their entry files contain no write call at all. The shipped sweep
therefore asks git what changed after each run instead of asking the source what
it might do, and restores the paths that changed. Over a full 185-script run the
working tree is left clean apart from the report itself — confirmed by
`git status --porcelain` after each of four runs.

**Behavioral suite, same command either side.** `npx jest src/__tests__/behaviors`:
**27 suites / 284 tests / 0 failing before → 28 suites / 299 tests / 0 failing
after.** The 15 new cases drive the real module in a subprocess, so a mutation of
the shipped file is a mutation of what runs.

**Nine mutations of the real controls, nine caught.** Each was applied to the
shipped file, the suite run, and the file byte-restored and diff-confirmed after
each:

| Mutation | Tests failed |
|---|---|
| `writesRepoFiles` hard-wired false | 1 |
| every failure relabelled `needs_environment` | 4 |
| the empty-environment predicate removed | 3 |
| the usage predicate's line anchor dropped | 1 |
| the `needs_arguments` branch removed | 1 |
| the failure-line preference removed | 1 |
| the credential shape narrowed back to a name list | 1 |
| the registry kind filter removed | 1 |
| the refusal to run a command reaching outside the checkout removed | 1 |

The failure-line mutation **survived on the first attempt**, which is the point
of running them: the suite had no case for the shape that control exists for — a
script that states its problem in prose and then prints a bare verdict. The case
was added and the mutation then failed 1 of 15. The number in the table is after
that repair.

**Both directions are pinned, because a predicate tightened until nothing is a
real failure is as useless as none.** Three cases assert that an unset credential,
a refused connection and a usage message are not defects; three assert that a
failure report which merely mentions a database, or describes usage mid-sentence,
still is one.

**Reproducibility.** Two full runs of the same 185 scripts agreed on the outcome
and the writer flag for **every one of the 185**. A third, fourth and fifth run,
after the classifier was corrected, reproduced 114 / 58 / 11 / 2 exactly. The
only quantity that moved across all five runs was the writer count, by one, for
the reason given under Known Gaps.

**The correction those later runs record, and why the first number was wrong.**
The first version matched credentials against a hand-kept list of variable names
and missed two that were not on it, counting two empty environments as defects;
it also had no category for a script that simply was not given its arguments. The
first run therefore reported 67 failures. Matching a credential by shape rather
than by name moved 9 scripts out of the failure count, and the honest figure is
58. A hand-kept list of names is the same mistake as a hand-kept list of tenants.

**Other checks.** `NODE_OPTIONS=--max-old-space-size=6144 npx tsc --noEmit
--pretty false` exit 0 with `tsconfig.tsbuildinfo` removed first, 0 diagnostics.
`npx eslint` exit 0 on both changed files. `node
scripts/audit/ci-gate-registry-check.mjs` passes at 213 scripts, 18 pull-request
gates unchanged.

## Known Gaps

- **`passed` means exited 0, not sound.** Several of these scripts scan a file
  that no longer exists, read an empty string, find nothing unsafe in it and exit
  0. That class of vacuous check is a separate open item and this sweep does not
  detect it; a script that passes here may still be proving nothing.
- **The writer count is a floor, in two ways.** A write to a gitignored path, or
  anywhere outside the checkout, is invisible to the tree check. And the check
  sees *net change*, not the act of writing: a script that regenerates a
  committed report byte for byte reads as a non-writer. That second limit was
  observed rather than reasoned about — one entry moved from writer to
  non-writer between two runs, purely because the report it regenerates had been
  committed in between, which is why the earlier runs in this record report 90
  writers and the committed measurement reports 89. Neither number is wrong; the
  quantity is not stable, and the report names why.
- **One row describes the branch, not the repository.** `audit:layer-boundaries`
  runs against `origin/main..HEAD`, so its outcome depends on what the sweep was
  run on. It is the only branch-relative entry in the set and the report names it
  in `caveats`.
- **The measurement can go stale and nothing fails when it does.** Same open
  question as the other committed proof bundles: a generated file under version
  control needs a stated owner and a refresh moment, or it needs to leave version
  control. Recorded rather than solved here.
- **Classifying the 185 is not done.** This produces the evidence for that work;
  it takes none of the decisions.
