# 2026-10-07-coverage-census-merge-order-regen — Regenerate the coverage census after a merge-order drift

## Plain-English Summary

The committed test-coverage census under-counted the repository by two test
files. No one wrote a wrong number: each of three branches regenerated the
census honestly against the same base, and each added a different test file, so
all three produced the **same** totals. Because those hunks were byte-identical,
merging them produced no conflict and no warning — the drift exists only in the
merge ORDER, which no per-branch check can observe. The drift guard runs on a
branch against its base, and each branch was correct against its base.

This regenerates the census on current `main`. Total and covered both move by
two and the uncovered count does not change, so both newly merged suites are
reached by CI.

This is a bookkeeping correction. No product behaviour, schema, route, flag, or
gate changes.

## Known Gaps

- **The cause is not fixed, only its effect.** Two branches that each add a
  different test file and regenerate against a shared base produce identical
  census hunks, which merge cleanly and leave `main` short by one per extra
  branch. A per-branch drift guard cannot see this, because every branch is
  correct against its own base. Closing the class needs either a merge queue
  that re-runs the guard against the post-merge base, or a guard that runs on
  `main` after a merge rather than on the branch before it. Both are out of
  scope here and neither is attempted in this record.
- This record corrects the count as of the commit it is built on. A branch
  already open against an older base will reintroduce the same drift when it
  merges.
