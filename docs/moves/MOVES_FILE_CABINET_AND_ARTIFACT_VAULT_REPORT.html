Moves File Cabinet & Artifact Vault

Durable, versioned, governed artifact storage for every Strategic Move — Azure Blob + Postgres registry + File Cabinet UI. Implementation report.

1. The problem this closes

Before this work, generated deliverables lived in browser downloads or ephemeral API responses. Nothing was durably stored, versioned, or discoverable. A Move could not function as a professional engagement workspace because its artifacts had no home. This implementation makes the hard rule literal: no Move artifact exists only in browser Downloads or temp output — every one is saved to Azure Blob, has a Postgres metadata row, appears in the File Cabinet, and keeps its version history.

2.1 The registry table — move_artifacts

One row per artifact version. Carries Blob location (blob_container, blob_path, blob_sha256), file_size, version, a governed status (draft → preliminary → review_required → aligned → approved → board_ready, plus gap states like client_to_complete, evidence_missing, blocked), version lineage (supersedes_artifact_id / superseded_by_artifact_id), a lifecycle_state (current / superseded / retired), and quality signals (quality_score, unsupported_claims_count, citation_ready). Row Level Security scopes reads to the tenant key — no cross-tenant access.

3. Versioning

saveMoveArtifact computes the next version per (move, artifact_type) among current rows, writes the new row as lifecycle_state = current, and atomically marks the prior current row superseded with a back-pointer. Nothing is deleted — the File Cabinet's “Show version history” toggle reveals the full lineage. Every regeneration of the Charter produces v2, v3, … without losing v1.

4. The File Cabinet UI

A dedicated File Cabinet tab on every Move detail page. It reads the registry API and presents artifacts grouped by family, with per-family filter chips and counts, a current-vs-history toggle, and per row: title, format badge, version, governed status chip, phase, quality score, unsupported-claim count, file size, timestamp, an explicit ● Blob storage indicator, and Open / Download actions.

5. Download path — honest about storage

The download route streams the artifact bytes from Blob server-side via the object-storage adapter (download(container, path)) rather than minting a SAS URL — so it works under managed identity without user-delegation-key rights, and tenant isolation is enforced before a byte is read. The registry never lies about storage: an artifact whose bytes did not reach Blob is marked storage: unconfigured and the UI shows ○ no blob rather than implying it was stored.

6. Hard rules honored

  • Every artifact saved to Azure Blob. enforced
  • Every artifact has Postgres metadata. enforced
  • Every artifact appears in the File Cabinet. enforced
  • Version history preserved. enforced
  • No cross-tenant access (RLS + tenant-key checks on read/download). enforced
  • No browser-only or temp-only artifacts. enforced
