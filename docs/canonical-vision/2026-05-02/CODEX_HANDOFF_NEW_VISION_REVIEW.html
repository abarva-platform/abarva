What changed since the last lock

Three meaningful shifts. Each has implications for code already written.

CHANGE 01
The chrome is named the Atrium pattern
No external reference. Our own design language. Top nav + horizontal submenu strip + agent zone (left, ambient by default) + canvas (right, dominant). Three agent states: ambient / engaged / focus. Submenu navigation preserves agent state.
CHANGE 02
Atrium applies to all six modules
Home, Setup, Strategic Moves, Source, Intelligence, Tower — all use the same chrome. Each module specifies its own submenu list, agent (Atlas / Steward / Nexus / Sentinel), and canvas content. Cross-module navigation preserves prior agent state.
CHANGE 03
Metrics-as-gap-engine
Critical metrics per industry / functional domain become corpus content. Tenant brings their metrics. Platform compares; surfaces quantitative gaps, measurement gaps, trajectory gaps. Gaps drive origination. Strategy ingestion ties to gap profile.

Detailed specifications for each change live in the companion documents below.

Sequencing principles for your judgment

You decide the sequence. The four documents don't prescribe an exact order because the right order depends on what you find when you walk the codebase. A few principles to ground your choice:

PrincipleWhat it means in practice
Data layer before page layer If a UI surface depends on a data model that doesn't exist yet, build the data model first. Don't ship UI that renders empty content.
Chrome before content The Atrium chrome (top nav, submenu strip, agent zone, canvas) is the substrate for everything else. Build it first; the modules' specific submenus and content fill it.
Corpus authoring runs async Metric record authoring doesn't block UI work. Author records continuously in the background while the chrome and surfaces ship. The first 50-100 Tier-1 records are enough to demo the gap engine; full corpus matures over time.
Migration vs. greenfield Where existing surfaces (live Programs, live Source) need to evolve to Atrium, treat as careful migration with tests. Where new surfaces are needed (Setup Metrics submenu, Intelligence with gap engine), build greenfield. Don't conflate.
Parallel where independent Chrome implementation, corpus authoring, agent prompt library, and migration of existing surfaces are largely independent. Run in parallel where dependencies allow.
Sequential where dependent Sentinel's structured-output emissions need the canvas dynamic-publication rendering layer to exist first. Tower module needs Strategic Moves to be on Atrium first. Sequence accordingly.
Demo tenants are the acceptance test Apex Retail, Meridian Health, First Capital. Each piece of work is "done" when it works for all three demo tenants without leakage or empty surfaces.

Document your sequencing decisions in commit messages. The founder shouldn't need to review your plan before you start, but they should be able to read your commit log and understand why work shipped in the order it did.
