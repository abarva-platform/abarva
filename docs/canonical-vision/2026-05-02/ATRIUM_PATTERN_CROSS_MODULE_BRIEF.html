The Atrium pattern, applied to all six modules.

One chrome shared across Home, Setup, Strategic Moves, Source, Intelligence, and Tower. Each module specifies its own submenus, agent identity, and canvas content. The discipline of consistency is the platform's signature.

01Mission & principles

Implement the Atrium pattern as the unified chrome across all six platform modules. The chrome is invariant — same top nav, same submenu strip pattern, same agent zone with three states, same canvas. What varies per module: the submenu list, the agent identity and voice, the canvas content shape.

Three principles that hold for every module

  1. Persistent zones. Top nav, submenu strip, agent zone, and canvas are always present. Their dimensions are locked.
  2. Context-driven canvas. Submenu click swaps canvas only. Agent state preserves across submenu navigation. Browser URL updates for deep-linking.
  3. Agent-mediated work. Each module has a designated agent. The agent's voice, role, and capabilities differ; the chrome behavior is identical.

Why consistency is itself the value

An enterprise platform's hardest UX challenge is fluency across modules. Users move between strategic thinking (Intelligence), portfolio management (Strategic Moves), vendor commitment (Source), and portfolio observation (Tower) within a single session. Every module-switch that requires re-orienting costs cognitive energy. The Atrium pattern's discipline is that the user never re-orients. They learn the chrome once; every module reuses it.

The ambition is not "consistent enough." The ambition is perfect chrome consistency, with the variation expressed cleanly through submenu list, agent identity, and canvas content. When users say "AbarVa just feels right to use" — this is what they mean.

02The chrome — locked

The chrome is invariant across modules. These dimensions and behaviors are not negotiable per-module.

ElementSpecBehavior
Top nav100% × 32pxAbarVa logo · tenant · six module names · user profile
Submenu strip100% × 36pxHorizontal tabs; module's submenu list; click swaps canvas only
Agent zone (ambient)200px wideAgent name, status indicator, ambient brief, last reply, composer
Agent zone (engaged)360px wideFull conversation, suggestion chips, active composer
Agent zone (focus)520px wideConversation as work surface; canvas reduced to reference panel
CanvasRemainderSelected submenu's content; reflows per agent state; receives published cards

State transitions (locked)

  • Ambient → engaged: click composer, type, or agent surfaces substantive output. ~250ms ease.
  • Engaged → ambient: 30s inactivity, or user clicks into canvas.
  • Engaged → focus: explicit user action only — chevron or "enter focus" affordance. Never auto.
  • Focus → engaged: click chevron or any submenu tab.
  • Module switch: agent state preserved in background; returning restores prior conversation.

04Home — Atlas

Personalized landing per entitlements. Atlas synthesizes the user's morning state across modules and surfaces what matters now.

Home
Atlas · synthesizer
Home — ambient state
Atlas brief · cross-module morning view

Atlas synthesizes across modules. The morning brief shows decision pressure (Source), upcoming events (Moves), realized value (Tower), and surfaced gaps (Intel) in one personalized view.

Submenus
Today · Calendar · Inbox · Recent activity. Today is default. Calendar is integration to user's calendar showing platform-relevant events. Inbox is mentions/handoffs/decisions awaiting user. Recent activity is the user's own recent platform actions.

Atlas — the synthesizer. Atlas reads across all modules the user has access to. Synthesizes morning state. Surfaces what matters in plain language. Doesn't dive into module-specific work; for that, the user goes to the module and meets the module's agent.

10Cross-module behavior

The chrome's discipline holds across module switches. The user moves through the platform fluidly without losing thread.

State preservation across module navigation

When the user switches modules, the previous module's agent state is preserved in background. Returning to that module restores the conversation in its prior state. This is the multi-module coherence that makes the platform feel like one tool, not six.

Example flow

Nina is in Intelligence working a thinking session about the OSA measurement gap. She switches to Strategic Moves to check whether the Analytics Warehouse move addresses this. She switches to Source to look at the BAFO situation. She switches back to Intelligence — her thinking session is still there, in the same state, mid-thought. That is the cross-module discipline.

Cross-module references and handoffs

Modules reference each other through structured links, not duplicate state. A Strategic Move's evidence ledger may reference an Intelligence session — clicking the reference opens that session in Intelligence. A sourcing event may reference a Strategic Move it's executing against — clicking opens the move. A Tower pressure card may reference both a sourcing event and a downstream move cascade — clicking opens whichever the user wants.

Agent handoffs

Sometimes work flows from one agent to another. Sentinel matures a candidate move and the user registers it — Sentinel hands off to Nexus at P0. The hand-off carries the conversation as evidence. Nexus picks up with full context. Atlas surfaces a pressure cascade — clicking opens the relevant move in Strategic Moves where Nexus takes over. Each agent owns its lifecycle but knows when to defer to another.

What the codex needs to support

  • Persistent agent state per (user, module) — not lost on module switch
  • Cross-module references rendered consistently with deep-link behavior
  • Agent handoff protocol — structured payload that one agent passes to another
  • Browser URL discipline that reflects module + submenu state
  • Entitlement-aware module list in top nav
  • Tenant-aware everything — pinned tenant context across all modules

11Delivery & reporting

Implementation sequence — your judgment

The right sequence depends on what you find in the codebase, what locks are held by other lanes, and where the data-layer dependencies live. The lane decides. A few principles to ground the choice:

PrincipleWhat it implies
Chrome before content The Atrium chrome is the substrate for every module's surface. Build it first as a reusable framework; modules then specify their submenu list, agent identity, and canvas content against that framework.
Prove the chrome on one module Before applying to all six modules, prove the chrome works correctly on one — most naturally Intelligence (where the design originated). Catch ergonomic issues there, then propagate.
Migrate the active surfaces carefully Strategic Moves and Source have substantial existing surface area and may be subject to in-flight rebuild work by other lanes. If those rebuilds are in progress, defer Atrium application to those modules until rebuild completes — apply Atrium to greenfield modules first.
Greenfield modules can ship first Setup's Metrics submenu is greenfield. Intelligence with the gap engine is largely greenfield. Home and Tower can be built on the chrome quickly. These have lower migration risk than Strategic Moves and Source.
Parallelize independent work Chrome implementation, agent prompt library authoring, dynamic-canvas rendering layer, and module-specific submenu wiring are largely independent. Run them in parallel where they don't share locks.
Sequence the dependent work Sentinel structured-output emissions need the canvas dynamic-publication rendering layer. Tower's portfolio observation needs Strategic Moves on Atrium. Home's cross-module synthesis needs other modules on Atrium. Sequence accordingly.

Document your sequencing choice in the EVENT_LOG entry that opens your work. Two to four sentences explaining why you sequenced the way you did. The founder reads commit logs, not work plans — your reasoning lives in the log, not in a separate review document.

Acceptance criteria

  • Top nav, submenu strip, agent zone, canvas dimensions match locked spec across all six modules
  • Three agent states (ambient/engaged/focus) work consistently with smooth ~250ms transitions
  • Submenu navigation preserves agent state across all modules
  • Browser URL updates reflect module + submenu state for deep-linking
  • Cross-module navigation preserves prior agent states in background
  • Each module has its specified agent (Atlas/Steward/Nexus/Sentinel) with appropriate voice
  • Canvas dynamic publication works (pattern cards, move seeds, etc. surface from agent emissions)
  • Mobile responsive behavior degrades gracefully — chrome restructures cleanly at narrow widths
  • Entitlement-aware module list and submenu list — users only see what they're entitled to
  • Tenant context pinned across all modules — no leakage

Open questions worth surfacing if encountered

The lane makes its own calls on these as they arise. Some may be obvious from the codebase; others may be genuine ambiguities. If a decision changes the platform's character meaningfully, surface it in the EVENT_LOG with your choice and reasoning rather than waiting for permission:

  • Migration risk for Strategic Moves and Source — if these are mid-rebuild by other lanes, defer Atrium application until rebuild completes
  • Mobile responsive behavior — at what widths do chrome elements compress, restructure, or hide; the lane decides based on the platform's actual usage patterns
  • Agent state machine framework choice — pick what supports state preservation across modules cleanly with minimum new dependencies
  • Cross-module reference rendering — visual treatment for "this links to a move in Strategic Moves" type references; decide based on the chrome's existing semantics
Continuous execution discipline Auto-approve and merge work within the lane after standard checks pass — tests, linters, locks respected, EVENT_LOG updated. The founder reviews the running platform, not work plans. Surface blockers in EVENT_LOG with enough context for unblocking. Trust your judgment on sequencing; document your reasoning in commit messages.
