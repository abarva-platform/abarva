# Pattern to Product Logic Model

## Purpose

Define when patterns should become product logic instead of remaining retrieved guidance.

## Patterns That Become Product Logic

Candidates for product logic:

- Fixed stages.
- Required gates.
- Artifact lifecycle.
- Approval routing.
- Scorecard lock before evaluation.
- Cannot cite unparsed document.
- Required waiver rationale.
- Value cannot be realized without evidence.

## Patterns That Remain Guidance

Usually remain retrieved guidance:

- Negotiation questions.
- Value levers.
- Risk explanations.
- Executive summaries.
- Diagnostic questions.
- Vendor trap explanations.
- Benchmark interpretation.

## Criteria for Product Logic

A pattern should become product logic when:

- The rule is deterministic.
- The rule prevents unsafe workflow movement.
- The rule protects evidence integrity.
- The rule is stable across customers or archetypes.
- The rule can be validated in fixtures.
- The user impact of violating the rule is high.

## Criteria for Guidance

A pattern should remain guidance when:

- The advice depends on expert judgment.
- The action varies by context.
- The pattern is still evolving.
- The evidence is qualitative.
- The rule cannot be applied deterministically.

## Hybrid Patterns

Some patterns produce both logic and guidance.

Example: Scorecard defaults.

- Product logic: evaluation cannot begin if scorecard is not locked.
- Guidance: commercial weight override should be explained and justified.

## Change Control

Promoting a pattern from guidance to product logic requires:

- Pattern version.
- Validation fixture.
- Acceptance criteria.
- Migration impact review.
- Founder/product approval.
