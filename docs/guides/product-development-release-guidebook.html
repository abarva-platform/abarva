AbarVa operating guidebook

Product development and release for pilot-ready environments

The future way of building AbarVa: many contributors, many agents, one release spine. This guide turns today's lab habits into a governed Product Dev, Product Preview, and Product Prod operating model that can support pilot clients and new team members.

1. Why This Exists

The lab style was optimized for founder speed. The product style must be optimized for pilot trust, team coexistence, and repeatable deployment evidence.

Today risk

  • Multiple agents can deploy unrelated changes into the same live surface.
  • Runtime state can drift from merged code or from the intended image digest.
  • Backlog intent, PR scope, release evidence, and browser proof are separated.
  • New contributors cannot tell which lane is safe without asking Anand.

Target behavior

  • Every change has one backlog item, one owning branch, and one release record.
  • Dev absorbs iteration. Preview absorbs release-candidate rehearsal. Prod stays boring.
  • Agent work is isolated, reviewable, and mergeable without hidden operational side effects.
  • Client pilots get evidence, rollback, ownership, and signed-in proof by default.

Product rule

No one, human or agent, calls a change ready for pilot clients because code merged, an image built, or a health endpoint returned green. Readiness means the right environment, the right data boundary, the right identity boundary, and the right signed-in user journey all pass with captured evidence.

2. Environment Model

The Product lane has three shared environments. Client private planes are separate lanes and should not be confused with Product Prod.

Environment Purpose Allowed work Not allowed Exit gate
Product Dev Integration lane for active product development. Feature integration, schema rehearsal, synthetic data, auth setup, module QA. Client production claims, public DNS cutover, destructive data moves. Focused tests, release record, Dev deployment proof, signed-in smoke when route-facing.
Product Preview Release-candidate proving ground. End-to-end rehearsal, client-pilot dry run, migration rehearsal, stakeholder QA. Unreviewed experiments, direct agent hotfixes, unapproved client data loading. Go/no-go evidence packet, browser proof, rollback rehearsal, data and auth checks.
Product Prod Stable shared product runtime. Approved release promotion only, monitored fixes, controlled flags. Direct-to-prod agent work, branch image tests, ad-hoc env changes, unproven migrations. Runtime invariant, traffic proof, signed-in proof, release status update.
Client Preprod Client-specific rehearsal plane. Private data onboarding, tenant-specific integration, SSO rehearsal. Shared Product Prod mutation, synthetic claims presented as client truth. Client data lineage, retrieval proof, SSO proof, security approval.
Client Prod Client-specific production plane when sold or approved. Client-approved production workloads only. Lab experimentation, shared demo data, unapproved model/data egress. Signed client go/no-go, rollback, monitoring, support owner.

Promotion principle

The default path is Product Dev to Product Preview to Product Prod. A client data or private-plane lane adds Client Preprod before Client Prod. Skipping a lane is a named exception, not a habit.

3. Agent And Workload Rules

These rules make multi-agent work possible without turning the platform into a race between whoever deployed last.

Branch discipline

  • Start from current origin/main.
  • Use one branch per backlog slice.
  • Do not mix unrelated local changes into a release branch.
  • Open a PR. Do not push directly to main.

Runtime discipline

  • Do not use Vercel as product runtime evidence.
  • Do not mutate shared ACA traffic from a feature branch.
  • Use digest-pinned images for ACA web and worker runtime.
  • Run runtime invariant checks after deploy or env changes.

Data discipline

  • Data builds run as ACA Jobs, not web requests.
  • Report loaded, indexed, retrievable, cited, and answer-used separately.
  • Never send raw ungoverned context to Claude.
  • Tenant scope and source lineage are mandatory.
Action Allowed owner Required proof
Build product web image Repo-owned ACA deploy workflow Git SHA, image digest, ACR policy check, Buildx cache used
Promote to Product Preview or Prod Release owner through approved lane Release record, runtime invariant, health check, signed-in smoke
Change env vars or secrets Named operator with release record Secret reference proof, no value exposure, runtime invariant after change
Run data migration or build Data-plane owner through ACA Job Dry run, idempotency key, proof bundle, validation output, rollback plan
Prune ACR images Ops owner only Dry run first, keep active digest and rollback window, named approval for untagged purge

4. Backlog Operating System

The backlog is not just a list of ideas. It is the control surface that tells agents what to build, what not to touch, how to prove it, and where it may be released.

1. IntakeCapture problem, user, client impact, and why now.
2. ClassifyAssign lane, module, environment, risk, owner, and proof bar.
3. SliceCut into PR-sized work that one agent or engineer can own.
4. BuildImplement on a branch with tests and release record.
5. ProveRun local, deployed, signed-in, and data checks as applicable.
6. CloseUpdate backlog state with PR, deploy, screenshots, gaps, and next slice.
Status Meaning Move forward when
Intake Problem is known but not shaped. Owner, client impact, and release lane are named.
Ready to slice Scope is clear enough to break into agent work. Acceptance criteria and proof artifacts are written.
In progress One owner is actively building. PR includes tests, release record, and evidence.
Preview candidate Ready for Product Preview rehearsal. Preview smoke and go/no-go evidence pass.
Released Promoted to intended environment. Runtime proof, browser proof, and backlog closure are linked.
Blocked Needs decision, dependency, credential, data, or design input. Blocker owner and next decision date are explicit.

Backlog item must include

  • Problem statement and desired user outcome.
  • Release lane and target environment.
  • Client applicability: all clients, specific tenants, internal only, or demo only.
  • Files/modules likely touched and collision warning if another PR touches them.
  • Acceptance criteria with commands and browser proof.
  • Rollback or disablement approach.

Weekly backlog review

  • Review pilot blockers first: auth, data, retrieval, module-critical UX, security.
  • Promote only items with evidence, not optimistic status.
  • Archive stale lab experiments that are not attached to a product lane.
  • Reserve explicit capacity for bugs found by deployed browser QA.
  • Keep a visible "do not start" list for gated migrations or client data moves.

5. Release Flow

Every release walks through the same evidence ladder. The ladder is deliberately plain because it is how new team members and agents avoid overclaiming.

Step Question Required artifact
Code ready Does the change exist on a branch with the expected diff? PR, focused diff, tests, release record.
Merged Did the PR land in main? Squash merge commit and updated release record.
Built Was the exact merge SHA built into an image? ACR tag, digest, Buildx cache proof, ACR SKU proof.
Deployed Is the target ACA revision running the exact digest? Container App image, traffic revision, health response.
Browser-visible Can the right signed-in user see and use it? Playwright screenshots, route URLs, console/network notes.
Data-usable Can the app read, retrieve, cite, and answer from the right data? Counts, lineage, retrieval proof, answer transcript, tenant fence proof.

Language standard

Use precise status words. Say "merged", "deployed", "browser-visible", "signed-in proven", "retrieval-proven", or "blocked". Do not compress those states into "done".

6. Proof Standard

Proof is what lets a pilot buyer, auditor, founder, or new engineer trust the platform without needing to know which agent made the change.

Code proof

  • git diff --check on touched files.
  • Focused unit or integration tests.
  • npm run release:check when release-relevant.
  • Architecture/provider audits for runtime or data-plane changes.

Runtime proof

  • Image digest and active ACA revision.
  • 100 percent traffic target for the expected revision.
  • Health endpoint with Postgres and graph/data-plane status.
  • Worker job image match when worker behavior changed.

Experience proof

  • Signed-in route screenshots.
  • Representative happy path and failure path.
  • Client-friendly response quality review.
  • No raw IDs, unexplained metrics, or internal debug language.
Change type Minimum proof Extra proof before pilots
Static doc or guide Link check, visual open, release record. Founder/team review and backlog adoption.
UI or route Focused tests, browser screenshot, console check. Signed-in role test in Product Preview and Prod smoke if promoted.
Auth or tenant access Clerk/user metadata proof without secret leakage. Per-tenant login, route access, tenant fence, sign-out/re-entry.
Data or retrieval Dry run, lineage, counts, row/chunk facts, retrieval transcript. Tenant-scoped browser answer QA with citations and screenshots.
Migration Dry run, destructive scan, rollback plan, empty-env replay if possible. Preview rehearsal, backup/restore posture, go/no-go approval.

7. Pilot Client Readiness

Pilot readiness is a product and operations claim. It is not the same thing as a feature demo.

Must be green

  • Product Dev and Product Preview are operational and current.
  • Clerk or client SSO works for test personas in the target environment.
  • Tenant metadata, default client, and roles are correct.
  • Home, Intelligence, Moves, Source, and Tower route smoke passes.
  • Client data sources have lineage, governance status, and retrieval proof.
  • Rollback is rehearsed or operationally credible.

Must be explicit

  • Which tenant data is synthetic, client-provided, or interview-derived.
  • Which insights are deterministic versus Claude-generated narrative.
  • Which datasets are loaded, indexed, retrievable, cited, and dashboard-visible.
  • Which modules are in pilot scope and which are intentionally hidden.
  • Who owns incidents, data corrections, client access, and release approval.

Current blocker class

Auth cannot be hand-waved. If Clerk variables exist but signed-in routes redirect, loop, time out, or fail hosted sign-in, the environment is not pilot-ready. The guidebook treats that as a release blocker until signed-in browser proof passes.

9. Emergency And Break-Glass Path

Emergencies need a path, but they should leave better evidence than normal work, not less.

  1. Name the incident, affected environment, affected clients, and rollback owner.
  2. Prefer rollback to last known good digest before forward-fixing Prod.
  3. If a direct Azure mutation is unavoidable, record exact command intent before execution.
  4. After mutation, prove image digest, revision traffic, health, and signed-in route behavior.
  5. Create a follow-up PR that captures the fix, release record, and postmortem notes.

Forbidden emergency shortcuts

Do not quietly change Prod env vars, traffic, secrets, or data-plane state and call it a small fix. Emergency work is allowed only when the operator leaves a durable audit trail and restores the normal release lane afterward.

10. New Joiner Start

A new engineer or agent should be productive without gaining unsafe power over the production lane.

First day reading

  • AGENTS.md
  • docs/releases/RELEASE_CONTROL_POLICY.md
  • docs/runbooks/deploy-authority-and-runtime-invariant.md
  • docs/ops/aca-data-build-job-rule.md
  • This guidebook

First week permissions

  • Read access to repo, backlog, release records, and evidence folders.
  • PR author rights before deployment rights.
  • Product Dev validation before Product Preview or Prod access.
  • No direct subscription owner rights unless a role-specific approval exists.
