## Walk 3 · Last-updated timestamp is live

| Pattern | `lastUpdatedAt` | Source file |
| --- | --- | --- |
| `owned-brand-margin-recovery` | 2026-04-23T03:45:24.000Z | `08-owned-brand-margin-recovery.md` |

| `fraud-detection-modernization` | 2026-04-23T03:45:24.000Z | `10-fraud-detection-modernization.md` |

**Source derivation:** `generate-pattern-manifest.ts:102` reads
`statSync(join(SOURCE_DIR, sourceFile)).mtime.toISOString()` — the timestamp is
live from the pattern markdown file's modification time, not hardcoded.

**Render path:** Pattern page reads the manifest's `lastUpdatedAt` field and
passes it through `formatFreshness()` (relative: "today" / "1d ago" / "Nd ago")
or the tenant shell's `formatSeedFreshness()` for the metric grid.

**Caveat to flag to user:** all four patterns share an identical timestamp,
which means the manifest was regenerated in a single pass rather than reflecting
per-file edits. The mechanism is live; the regeneration cadence is not. The
manifest is **not** auto-regenerated on build — it lives as a committed JSON
file and requires `npm run intel:patterns:generate` to refresh. If a source
file is edited and the manifest isn't rebuilt, the rendered timestamp will
lag.

## Summary

All three walks pass at the resolver layer. The data contracts guarantee
bidirectional link integrity and tenant-overlay correctness; no UI defects
observed.

**One non-blocking observation:** pattern manifest regeneration is manual.
Recommend either a CI check that re-runs `intel:patterns:generate` on PRs
touching `Downloads/Patterns/**` and diffs the output, or a prebuild step that
regenerates whenever any source file mtime exceeds the manifest's own mtime.
