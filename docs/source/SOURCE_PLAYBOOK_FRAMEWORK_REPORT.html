AbarVa Source — Playbook & Stage-Gate Framework

How Source behaves like a senior sourcing engagement workbench: it shows the full professional standard, exposes gaps and the risk of proceeding, and lets the Maestro/Admin advance with gaps — transparently — without ever faking completeness.

1 · Design principle

Source is not a generic RFP generator. It is a governed sourcing decision platform. The product states: "Here is what a best-practice sourcing event should include. Here is what you have. Here is what is missing. Here is the risk of proceeding. Maestro can approve moving forward with gaps, and we carry those gaps forward transparently." Gaps are allowed; gaps are never hidden; completeness is never faked.

2 · The universal Source spine

Every Source event follows a common 14-step spine (origination → archetype classification → intake/evidence readiness → current-state baseline → sourcing strategy → RFP design → vendor engagement → proposal intake → evaluation → commercial/pricing → negotiation → executive recommendation → contracting handoff → post-award controls). Each archetype specializes the evidence, sessions, RFP sections, pricing model, evaluation criteria, negotiation levers, deliverables, and gates — no single hardcoded RFP flow.

3 · Event archetypes

Source is built around SourceEventArchetype (merged in #3374). The first fully-implemented archetype is AMS_IT_OUTSOURCING; the framework is designed to extend to application modernization, cloud migration, ERP/SI selection, data/AI platform sourcing, GenAI/agentic platform sourcing, cybersecurity services, SaaS selection, BPO, vendor consolidation, renewal/renegotiation, and staff augmentation.

4 · The three-level Maestro Stage-Gate (PR #3391)

Every stage gate exposes three levels, computed by assessStageGate:

LevelMeaningIn code
Recommended standardWhat good looks like — the full set of evidence, sessions, reviews, decisions, and artifacts.all StageGateRequirements
Minimum-viable gateThe smallest responsible bar to advance without an override.requirements with tier: 'minimum_viable'
Maestro overrideAdvance despite gaps — with rationale, gaps acknowledged, risks accepted, follow-ups, and a preliminary label.applyMaestroDecision

Gate statuses

ready ready_with_gaps preliminary_only client_to_complete needs_review maestro_override_approved blocked

Hard rules enforced in code

  • Advancing past gaps requires a rationale (no silent approval) — the gate-decision API returns 422 otherwise.
  • An artifact is never marked final / issue-ready while gaps exist — a plain "approve" with gaps is honestly recorded as maestro_override_approved with a preliminary label.
  • Gaps + risks are carried forward (defaulted from the assessment if the approver didn't restate them).
  • Every decision yields a persistable ApprovalRecord with a readiness snapshot.

6 · Nexus/Sentinel gate guidance

buildGateGuidance turns an assessment into senior-advisor language — never just "approved" / "blocked": "The full standard for RFP Package Design is 5 items; 2 are met (40%). Missing: final evaluation weights, procurement review, legal review. If you proceed, these stay preliminary and cannot be marked issue-ready: evaluation_criteria, contracting_terms. You may proceed with Maestro approval, but the affected deliverables must remain preliminary and the gaps are carried forward."
