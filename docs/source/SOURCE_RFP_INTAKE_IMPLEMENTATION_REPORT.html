Source — RFP, Evidence Intake & Artifact Implementation

How a sourcing event moves from missing evidence to a board-grade, citation-disciplined, durably-stored RFP package — with every section honestly labelled.

1 · The 4-mode RFP section model (#3381)

Every RFP/RFx section resolves to one of four modes, so Source never silently ships a weak section:

ModeMeaning
AUTO-GOVERNEDGenerated from governed, cited client evidence.
AUTO-TEMPLATEStandard RFP/procurement boilerplate — polished by Claude, marked review-required.
ELICITMissing client-specific input — Nexus asks / requests upload or template.
CLIENT-COMPLETEClient / procurement / legal / commercial decision — AbarVa must not invent.

Each section carries an explicit label: issue-ready preliminary evidence missing client to complete legal review required procurement review required pricing review required blocked

2 · Evidence readiness ladder

Evidence is only truly ready when it is current, tenant-scoped, fact-backed, indexed, retrievable, citation-ready, promotion-evaluated, and context-bundle-proven. "Chunks exist", "records exist", "facts exist", and "indexed" are each insufficient. agent_ready is earned, never assumed.

3 · AMS evidence families & completion paths (#3381)

Every AMS evidence family has concrete completion paths — upload source file, download template & upload, answer in chat, mark client-to-complete, mark assumption (preliminary), or skip. 14 families: ticket/incident volumes, SLA baseline, labor/staffing, run-cost, vendor contracts, application inventory, infra/cloud estate, IT/retained org, transition constraints, security/compliance, evaluation criteria (client-complete), procurement timeline, legal terms (client-complete/legal-review), pricing preferences.

4 · Captured intake → governed context

Captured answers/uploads become governed objects — never chat-only, never auto-promoted to agent_ready. Chat answers are user_attested / captured; uploads are promotion_candidate after commit+index; promotion to agent_ready requires the governed ladder (verified live on SkyHarbor: an uploaded ticket-volume family was committed → governed-promoted → the affected current-state section lifted evidence_missing → issue_ready).

5 · Board-grade document generation

Major deliverables use the Deliverable Intelligence Orchestrator: a six-pass flow (architect → evidence-grounding → full-draft → red-team → board-grade-rewrite → render-package) on claude-opus-4-8, given both the governed evidence and an artifact-intelligence brief. Claude is told to use expert sourcing judgment to improve structure/exhibits/tables, but every client-specific fact must be cited [n], marked an approved assumption, or a placeholder. A quality gate blocks export on unsupported claims, leaked internal ids, missing source register / decision / recommendation / risk table, or tiny formatting.

Live proof

On SkyHarbor AMS the live run produced a 39,356-char board-grade RFP that self-organized into an internal decision memo / bidder-facing RFP / internal annexes (disclose-vs-withhold tiering); incumbent spend was excluded from the bidder-facing evidence. The real quality gate passed: 0 unsupported claims, 0 internal leaks, source register + decision + recommendation + risk table present, 25 client-to-complete items.

6 · Durable storage — File Cabinet / Artifact Vault (#3390, #3393)

No artifact exists only in Downloads/browser. Every generated deliverable, uploaded evidence file, template, session artifact, and approval packet is uploaded to Azure Blob (canonical paths under source-events/{tenant}/{event}/…), registered in the source_artifacts Postgres table, and surfaced in the per-event File Cabinet UI — grouped, versioned (regeneration supersedes; history preserved), and re-downloadable. The generator→cabinet bridge persists DOCX + HTML preview + Excel companion as independently-versioned artifacts; Maestro approvals persist as durable approval artifacts.

7 · Citation discipline & context bundle trace

Every generation emits a context-bundle trace (evidence requirements resolved, eligible vs missing families, retrieval results, current vs superseded fact counts, citation-ready count, confidence/source-basis distributions, grounding status, model-input hash, claims detected/supported/unsupported, tenant-leakage status). Internal source ids/tags never appear in the body; the source register exposes only label + family + confidence + as-of.
