# Source · Document format map by stage

For each of the 11 stages and 33 canonical artifacts, what document
formats does the artifact need over its lifetime? This map drives
which renderers we build and in what order. It also drives which
artifacts the agent can generate vs which must be uploaded.

## Format meaning

| Format | When | Notes |
|---|---|---|
| **md** | Always — the inline-authored body on the canvas | The lowest-friction authoring surface. Persisted to `source_event_artifact_states.body`. Already shipped. |
| **docx** | When the artifact ships externally (vendors, exec board, signatories) | Must look like a real Word document — headers, page numbers, signature blocks. The Programs module already has docx renderers we can mirror (`lib/programs/exports/renderers/`). |
| **xlsx** | When the artifact is fundamentally tabular / has calculations / weights / financial models | Authoring in markdown is unnatural. Either generate from structured data or accept uploaded `.xlsx` and parse. |
| **html** | When the artifact ships to a web surface (Confluence, SharePoint, the executive dashboard) | Renders pretty in browsers, embeddable, printable. |
| **pdf** | When the artifact is signed / archived | Frozen, immutable, signed digitally. Usually generated from docx or html. |

## Generation source

| Source | Meaning |
|---|---|
| **agent** | Generated by Claude with bound context (tenant + event + upstream artifacts). |
| **upload** | User-supplied file (paperclip). Vendor responses, contracts, baseline packs. |
| **hybrid** | Agent drafts; human edits; final exported. |

## Build order (informed by this map)

The map drives a clear priority. Build the formats that block the most artifacts first.

### Slice 1 · Markdown body via Claude (all 33 artifacts)

**Status: shipping next.** Adds a `Generate with Sentinel` button that calls Claude with bound context (tenant + event + upstream approved bodies) and writes the result to `source_event_artifact_states.body`. Single endpoint with per-artifact prompt templates. Unlocks every artifact at md tier. **Sequence to start with: d09_rfp_pack** because it's the highest-value vendor-facing artifact and exercises the full upstream-context pattern (needs d01 strategy + d05 scope as input).

### Slice 2 · Source-side docx renderer

Mirror the Programs `lib/programs/exports/renderers/` structure → `lib/source/exports/renderers/`. One renderer per docx-target artifact, starting with the four highest-value:

1. **d09 RFP Package** — sections for scope, evaluation criteria, response checklist, signature pages
2. **d24 Decision Brief** — Atlas voice, exec packet style, signature blocks
3. **d05 Scope Memo** — vendor-facing
4. **d27 Selection Memo** — award announcement

Pattern: each renderer takes the markdown body + structured event metadata + tenant info → emits a styled docx via the `docx` package. Download button on the artifact card; bytes registered in `source_artifacts` registry under `source-artifacts` Supabase Storage bucket.

### Slice 3 · xlsx generator (data-heavy artifacts)

Source-side xlsx renderer. Highest-value first:

1. **d16 Evaluation Scorecard** — weighted scoring matrix with rater rows, vendor columns, deviation calc
2. **d19 Pricing Normalization Workbook** — pricing line items normalized to assumption set, TCO calc
3. **d32 Value Ledger** — projected/committed/measuring/realized columns
4. **d04 Application Inventory** — tier/criticality/owner

Pattern: each takes structured event substrate (not just markdown) → emits xlsx via a renderer module + `xlsx` or `exceljs` package. Same registration flow as docx.

### Slice 4 · html / pdf for distribution

For the few artifacts that ship to web surfaces or get archived:

- **d24 Decision Brief html** — embeddable in Confluence/SharePoint
- **d24/d25/d26 pdf** — signed and frozen for the audit archive
- **d32 Value Ledger html** — embeddable dashboard view

### Slice 5 · Upload + parse pipeline (already partially built)

The `/api/v1/source/{eventId}/artifacts/upload` endpoint exists and handles:
- File bytes → `source-artifacts` Storage bucket
- Registry row in `source_artifacts`
- Synchronous text-parser pass (text/markdown only today)

Gap to close:
- Surface a **paperclip-upload UI** on the artifact card for upload-typed artifacts (d04, d07, d13, d19, d28, d31)
- Wire the `linked_artifact_id` bridge so the canvas Document tab can render the uploaded file's parsed text
- For docx/xlsx uploads, run mammoth + xlsx parsers (already partially in `lib/source/artifact-registry/text-parser.ts`)

## What this map costs

Realistic effort per slice, assuming one experienced engineer:

| Slice | Scope | Effort |
|---|---|---|
| 1 · Markdown via Claude | 1 endpoint + prompt builder + per-artifact prompt templates + UI button | 2–3 days |
| 2 · docx renderers | 4 renderers + download button + registry wiring | 4–5 days |
| 3 · xlsx generators | 4 generators + structured-data binders + download button | 5–7 days (the value ledger and scorecard are non-trivial) |
| 4 · html / pdf | 3 html templates + 4 pdf renderers (via puppeteer or existing docx → pdf path) | 3–4 days |
| 5 · Upload polish | Paperclip UI + linked_artifact_id wiring + parser surface | 2–3 days |

Total: ~16–22 days of focused work to get all 33 artifacts to their full target format set. Far less to get the demo-credible top 8 (d01, d05, d09, d16, d19, d24, d27, d32) covered in their primary format.
