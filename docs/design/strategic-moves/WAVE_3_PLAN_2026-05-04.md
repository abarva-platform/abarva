## Wave 3 scope (proposed)

Three migrations + one small schema add + one runner + one verification
report, matching the PR-3b / PR-4 / PR-B pattern.

### 3a · `deliverables_v2` backfill for the 20 moves with zero coverage

**Migration:** `20260504230000_strategic_moves_deliverables_backfill.sql`

- Target: 20 demo moves (5 demo clients, `client_id` scoped) with
  zero existing `deliverables_v2` rows.
- Seed 4–12 `deliverables_v2` rows per move drawn deterministically
  from phase-appropriate entries in `deliverable_types` (i.e. if
  `current_phase = 4`, seed P0/P1/P2/P3/P4 deliverables up to 12
  total; pick the canonical ones per archetype).
- Per-type picking rule: **archetype-appropriate canonical D-codes**:
  - `platform_modernization` → d01/d02/d03/d04/d05/d06/d07/d12/d13/d14/d15/d19
  - `strategic_transformation` → d01/d02/d03/d04/d08/d09/d11/d14/d19/d22/d24/d28
  - `ai_product_enablement` → d01/d03/d04/d11/d12/d15/d21/d22/d23/d24/d27
  - `workflow_automation` → d01/d02/d05/d06/d08/d12/d15/d19/d22/d24
  - `operational_optimization` → d01/d02/d03/d07/d08/d09/d10/d15/d16/d19/d22/d28
  - (null) → `operational_optimization` fallback
- Status derived from phase: deliverables whose `applicable_phases`
  contain a phase < current_phase → `signed_off`; ≤ current_phase →
  `in_review`; > current_phase → `draft`.
- Stamp: `title` prefix `[wave3a_2026_05_04]` so the whole backfill
  is reversible.
- **Open question for you (W3-Q1):** Do you want me to also seed a
  `deliverable_versions` row per new deliverable (with minimal
  placeholder content), or just the `deliverables_v2` shell? The
  detail view currently reads from `deliverables_v2` only
  (per `fetchMoveDeliverables` at transformers.ts line ~727), so
  the shell is sufficient for rendering. Content versions are only
  needed if you want the deliverable detail page to render
  something real. **My pick: shell only. Versions stay empty; we
  backfill content later if needed.**

### 3b · `engagement_deliverables` rehabilitation (dual-key)

**Migration:** `20260504231000_engagement_deliverables_engagement_id_column.sql`

Per your Q4 lock-in earlier: **option (a) — add `engagement_id` column
to `engagement_deliverables`**, dual-key with the existing `phase_id`.
The 12 existing rows in `engagement_deliverables` are orphan (keyed
on `phase_id` that no longer resolves); add the `engagement_id`
column, leave `phase_id` in place, and attempt to backfill
`engagement_id` from `phase_id → engagement_phases.engagement_id`
where the mapping still exists.

- Add column: `engagement_id UUID REFERENCES engagements(id) ON DELETE CASCADE`
- Backfill: `UPDATE engagement_deliverables SET engagement_id = ep.engagement_id FROM engagement_phases ep WHERE engagement_deliverables.phase_id = ep.id`
- Add index: `CREATE INDEX IF NOT EXISTS idx_engagement_deliverables_engagement_id ON engagement_deliverables(engagement_id)`
- **Don't** deprecate `phase_id` yet — leave for a later migration.

**Open question (W3-Q2):** If the backfill can't resolve any of the
12 rows (e.g. phase_id references were deleted), should the migration
(a) leave them NULL, (b) hard-delete them, (c) fail loudly? **My
pick: (a) leave NULL, log count, move on.** No silent deletion.

### 3c · unified artifact index view

**Migration:** `20260504232000_move_artifact_index_view.sql`

Create a SQL VIEW (not a materialized view, not a table) named
`move_artifact_index` that UNION ALLs the four artifact sources
keyed on `engagement_id`:

```sql
CREATE OR REPLACE VIEW move_artifact_index AS
  SELECT
    engagement_id,
    'deliverable'::text AS artifact_type,
    id::text AS artifact_id,
    title,
    NULL::text AS summary,
    deliverable_type_key AS artifact_kind,
    status,
    NULL::int AS phase_number,
    created_at,
    updated_at
  FROM deliverables_v2

  UNION ALL

  SELECT
    engagement_id,  -- engagement_deliverables.engagement_id (new column from 3b)
    'legacy_deliverable'::text,
    id::text,
    title,
    NULL,
    document_type,
    NULL::text,
    NULL::int,
    generated_at AS created_at,
    generated_at AS updated_at
  FROM engagement_deliverables
  WHERE engagement_id IS NOT NULL  -- post-3b backfilled rows only

  UNION ALL

  SELECT
    program_id AS engagement_id,
    'evidence'::text,
    id::text,
    title,
    summary,
    evidence_type AS artifact_kind,
    NULL::text,
    phase AS phase_number,
    created_at,
    created_at AS updated_at
  FROM program_evidence_items

  UNION ALL

  SELECT
    program_id AS engagement_id,
    'attachment'::text,
    id::text,
    original_name AS title,
    NULL,
    mime_type AS artifact_kind,
    scan_status AS status,
    phase AS phase_number,
    created_at,
    created_at AS updated_at
  FROM program_attachments
  WHERE deleted_at IS NULL;
```

**Downstream consumer (not in this PR):** the Strategic Moves detail
view already renders deliverables from `deliverables_v2` and
evidence from `fetchLinkedEvidence`. Once the view exists, a single
query `SELECT * FROM move_artifact_index WHERE engagement_id = $1
ORDER BY created_at DESC` replaces the multi-query dance. The view
is non-disruptive — downstream code migrations can follow at their
own pace. **This PR only adds the view; no transformer changes.**

**Open question (W3-Q3):** Should the view also project a
canonical `actor_id` column (who created/uploaded the artifact)?
All 4 source tables have different actor columns (`created_by`,
`uploader_user_id`, `created_by_user_id`). Merging them into one
`actor_id` column is slightly messy. **My pick: leave
actor_id out of v1; add in a later view revision if needed.**

  unified artifact index. The view is created and available; the
  transformer switch to use it is a later PR (to keep this one
  substrate-only per the PR-3b / PR-4 / PR-B discipline).

## Hard rules (same as Waves 1 + 2)

1. Non-destructive — 3a is INSERT-only; 3b is ADD COLUMN + UPDATE on
   NULL; 3c is VIEW creation (no data touched).
2. Scoped — 3a stamps only rows whose `engagement.client_id` is one
   of the 5 demo clients.
3. Idempotent — 3a uses `WHERE NOT EXISTS` on the stamp; 3b uses
   `ADD COLUMN IF NOT EXISTS`; 3c uses `CREATE OR REPLACE VIEW`.
4. Deterministic — 3a uses `hashtext(engagement_id || type_key)`
   for any stagger; no `random()`.
5. Reversible — 3a wipes on stamp; 3b drops column (with caveat
   that `engagement_deliverables.engagement_id` would be a
   destructive drop once referenced by the 3c view — in practice
   we'd reverse 3c first, then 3b); 3c is `DROP VIEW`.
