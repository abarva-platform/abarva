# Enterprise Information Architecture & Data Operating Model

**Status:** foundational. Every product surface, loader, adapter, template and agent session is an
implementation of this document. Where this document and any other document disagree, this one wins
until it is amended.

**Read this first.** If you are a Claude Code session, a Codex session, or an engineer touching
tenant data, templates, loaders, or any product surface, start here. Most of the expensive mistakes
in this codebase have been layer confusion, not bugs — an agent reading a projection as if it were
canonical, or treating an adapter's output as a source of truth. Those mistakes are invisible to
tests, survive reconciliation, and reach board slides.

---

## 1. The four layers

```
LAYER 1   CLIENT INTAKE          what the client gives us
          organised by WHO OWNS THE DATA, never by our schema
                  |
LAYER 2   SOURCE ADAPTERS        one adapter per intake tab
          the client never sees this
                  |
LAYER 3   CANONICAL ENTERPRISE   THE SOURCE OF TRUTH
          MODEL                  every object has an ID; every relationship lives here
                  |
LAYER 4   PRODUCTS               Home · Tower · Moves · Source · Intelligence · Learn · Pricing
          projections only — they read, they do not own
```

The single most important sentence in this document:

> **No product owns data. Every product is a projection of the Canonical Enterprise Model.**

Tower does not own spend. Home does not own applications. Moves does not own programs. Source does
not own vendors. They all read Layer 3.

---

## 2. Layer 1 — Client Intake

**Principle: the client must never think about our internal model.**

Intake is organised around **who in the client's organisation can produce the extract in one
action**. Not around our schema, and not as one giant template. A single workbook that requires
Finance, the PMO, the M365 admin and the CMDB team to co-author one sheet will never be returned
complete, because no one person can produce it.

One tab per data owner:

| Tab          | Who fills it                | Where it comes from                                      |
| ------------ | --------------------------- | -------------------------------------------------------- |
| Applications | CMDB team                   | ServiceNow, LeanIX, Apptio, Excel — we do not care which |
| Vendors      | Vendor management           | Contract register, Coupa, Ariba                          |
| Programs     | PMO                         | Clarity, Planview, Jira                                  |
| Copilot      | M365 admin                  | M365 admin centre usage export                           |
| ServiceNow   | ServiceNow admin            | Now Assist usage export                                  |
| GitHub       | GitHub admin                | Copilot / Codex org insights                             |
| ERP          | SAP / Oracle owner          | ERP extract                                              |
| Finance      | IT Finance / FP&A           | ERP GL, Apptio, Anaplan                                  |
| Benefits     | Business sponsors + Finance | Business cases, benefit tracker                          |
| Evidence     | Initiative owners           | Document store, signed sign-offs                         |

**Rules**

1. **A tab is defined by its owner, not by its schema.** If two teams own the data, it is two tabs.
2. **Accept the client's native export shape.** Normalisation is Layer 2's job, not the client's.
3. **Every tab ships with field-level guidance** — owner role, source system, how to extract,
   validation rule, worked example. Generated by `scripts/tower/build-template-field-guide.mjs`.
4. **A blank is a legitimate answer.** Blanks are reported as coverage gaps. Invented values are
   reported as fact, and they will be wrong on a board slide.
5. **We must fill our own reference pack better than we ask a client to.** Enforced: the field guide
   grades every field on whether our synthetic pack demonstrates it
   (`good` / `thin` / `filler_ramp` / `copy_paste` / `uniform` / `not_loaded` / `missing`).
   Anything below `good` is a field we have no standing to request.

## 3. Layer 2 — Source Adapters

**Principle: one adapter per intake tab. The client never sees this layer.**

```
M365 export        ->  Copilot adapter      ->  Tool, ToolUsage
ServiceNow export  ->  Now Assist adapter   ->  Tool, ToolUsage
GitHub export      ->  Copilot/Codex adapter->  Tool, ToolUsage
SAP export         ->  SAP adapter          ->  Spend, Vendor
CMDB export        ->  CMDB adapter         ->  Application, Platform
PMO export         ->  Portfolio adapter    ->  Program, Initiative
Finance export     ->  Finance adapter      ->  Spend, Budget
```

**Rules**

1. **An adapter emits canonical objects, never product shapes.** An adapter that emits something
   only Tower can read is not an adapter; it is Tower reaching into intake.
2. **Adapters preserve lineage.** Every emitted object carries `source_file`, `source_row`,
   `source_system` and `value_source` pointing **upstream at the client extract** — never at the
   adapter's own output. This is not optional bookkeeping; without it no number can be traced, and
   two files asserting different values for the same fact cannot be reconciled.
3. **Adapters are pure and re-runnable.** Same input, same output. No hand-editing of adapter output,
   ever. If the output is wrong, the input or the adapter is wrong.
4. **Adapter output is a build artifact, not a source.** It may be deleted and regenerated at any
   time. Nothing may treat it as truth.
5. **Adapters do not invent.** Where the client has no value, the canonical object carries a gap, not
   a plausible number. Any generated value is recorded in a synthetic manifest with its formula.

## 4. Layer 3 — The Canonical Enterprise Model

**This is the source of truth.** Not the workbook. Not SA09. Not Tower. Not `tower-standardized-v1`.

### Objects

Every object has a stable, typed ID.

| Object           | ID         | What it is                                              |
| ---------------- | ---------- | ------------------------------------------------------- |
| Organization     | `ORG-001`  | A business unit, operating company, or function's owner |
| BusinessFunction | `FUNC-001` | A function of the enterprise                            |
| BusinessProcess  | `PROC-001` | A process within a function                             |
| Capability       | `CAP-001`  | A business capability                                   |
| Application      | `APP-001`  | An application in the estate                            |
| Platform         | `PLAT-001` | Infrastructure or cloud platform                        |
| Vendor           | `VEN-001`  | A contracting entity                                    |
| Tool             | `TOOL-001` | A product licensed from a vendor (incl. AI tools)       |
| Program          | `PROG-001` | A funded programme                                      |
| Initiative       | `INIT-001` | A deliverable within a programme                        |
| AIUseCase        | `UC-001`   | An AI use case                                          |
| Risk             | `RISK-001` | A risk or control                                       |
| Metric           | `MET-001`  | A measured quantity                                     |
| Evidence         | `EVID-001` | The artefact backing a claim                            |
| Interview        | `INT-001`  | A captured conversation                                 |

### Relationships

Relationships live **here**, not in a product. A product may traverse them; it may not define them.

```
Application    supports        Capability
Capability     owned by        Organization
Application    hosted on       Platform
Vendor         owns            Tool
Tool           supports        BusinessProcess
Program        implements      AIUseCase
Initiative     part of         Program
Metric         measures        Initiative
Evidence       supports        Metric
Risk           applies to      Application | Initiative | Tool
```

Relationship verbs come from a canonical dictionary. Evidence notes, caveats and transformation
comments are **not** relationship verbs.

### Rules

1. **Identity is declared, never inferred.** An object's identity comes from its ID and its registry
   entry. It is never inferred from a directory name, a filename, or a folder's label.
2. **Every fact names its source of record.** Where two files assert the same fact, one is declared
   authoritative and the other reconciles to it. Silent divergence is a defect.
3. **Tenancy comes from the registry**, never from a hand-typed list and never from a path.
4. **Money is deterministic.** Canonical metric and fact tables own values. Claude owns narrative.
   A model may explain a number; it may never calculate spend, value, ROI or risk.
5. **Classification is a field, not a folder.** If an object is an AI initiative, a column says so.
   Living in a directory called `ai-control-tower/` is not a classification.

## 5. Layer 4 — Products

Home · Tower · Moves · Source · Intelligence · Learn · Pricing.

**Rules**

1. **A product owns presentation, never data.** It reads the canonical model and projects it.
2. **A product may not write back to Layer 3.** Corrections go to Layer 1 or 2 and flow forward.
3. **A product may not read Layer 1 or Layer 2 directly.** Reading intake or adapter output couples
   the surface to a client's export format and defeats the whole model.
4. **A projection may denormalise freely.** Marts, read models and view models are expected. They are
   derived, disposable, and rebuilt from Layer 3.
5. **The same object means the same thing in every product.** "Application" in Home and "Application"
   in Tower are the same `APP-001`.

### The distinction that keeps getting lost

These are three different things and must never be conflated:

|                           |                                                                                         |
| ------------------------- | --------------------------------------------------------------------------------------- |
| **Client CMDB**           | whatever they export — ServiceNow, LeanIX, Apptio, Excel                                |
| **Canonical Application** | `APP-001` with owner, vendor, criticality, lifecycle, hosting, capabilities, interfaces |
| **Home Application Grid** | a projection — summary, grid, relationships, insights                                   |

The same three-layer split applies to AI tools, to spend, and to everything else:

```
Client Copilot export  ->  Tool + Usage + Users + Cost + Owner  ->  Tower adoption / ROI / finance validation
Client SAP or Excel    ->  Spend + Vendor + Program + Category  ->  Tower spend dashboard
Client interviews      ->  Canonical enterprise objects         ->  Claude -> Home Book -> deterministic merge
```

## 6. Deterministic vs generated

|                                 | Owned by                   | May a model produce it?                                |
| ------------------------------- | -------------------------- | ------------------------------------------------------ |
| Facts, metrics, money, counts   | Layer 3 tables             | **No**                                                 |
| Relationships                   | Layer 3 dictionary         | No — a model may propose, a human approves             |
| Classification and tags         | Layer 3 fields             | A model may propose; the value is stored and auditable |
| Narrative, explanation, summary | Model                      | Yes                                                    |
| Recommendations                 | Model, grounded in Layer 3 | Yes, with citations                                    |

Every generated value carries a formula key and version, and is recorded in a synthetic manifest with
its source, its formula, and why it exists.

## 7. Enforcement — what makes this executable

Architecture that is not checked is architecture that is not followed. These exist today:

| Check                                               | What it enforces                                                                                                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `datasets/tenant-inputs/tenant-input-registry.json` | Declares the canonical input root per tenant. Legacy roots may not become active truth.                                                                         |
| `scripts/tower/fact-lineage-report.mjs`             | Per Tower/tenant-intake metric per tenant, every in-scope file asserting a value and whether they agree — `AGREE` / `CONFLICT` / `ONE_SOURCE` / `ABSENT`. Run default `quote` mode before quoting Tower or tenant-intake headline metrics; use `--mode migration-audit` for legacy drift analysis. |
| `scripts/source/source-substrate-lineage-report.mjs` | Per Source metric per tenant, every owning Source read model, Contract 360 projection, Cube, opportunity/evidence read model, or canary source asserting a value, with counting basis attached. Run before quoting Source portfolio value, contract/vendor counts, Contract 360 totals, optimization opportunity amounts, evidence-readiness counts, finance-confirmed value, or Cube/consumption metrics. |
| `scripts/tower/build-template-field-guide.mjs`      | Per-field ownership, source system, extraction guidance — and grades whether our own pack demonstrates it.                                                      |
| `npm run validate:context-corpus`                   | Governance policy on every context/corpus object.                                                                                                               |
| `src/lib/governance/context-corpus-policy.ts`       | Runtime contract; objects that evaluate to `block` never reach a model.                                                                                         |

**Still to build** (in priority order):

1. A canonical object registry with typed IDs and a relationship dictionary — Layer 3 does not yet
   exist as a single addressable thing.
2. An adapter conformance test: every adapter emits canonical objects with upstream lineage intact.
3. A layer-violation lint: no product module may import from an intake or adapter path.
4. Extend lineage reporting beyond Tower and Source headline metrics to every canonical object.

## 8. Current state, honestly

As of 2026-07-24 the codebase does not yet implement this document. Recorded so the gap is visible
rather than rediscovered:

| Layer       | Today                                                                                 | Gap                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1 Intake    | `datasets/tenant-inputs/active/<tenant>/current/` — registry-declared canonical input | Not yet organised as owner-scoped tabs; guidance now generated but the workbook does not exist                                       |
| 2 Adapters  | Partial, Tower-specific                                                               | Lineage is broken — in `tower-standardized-v1/`, **1,069 of 1,097 `source_file` values point at the file they are in**, not upstream |
| 3 Canonical | Does not exist as one model                                                           | `intelligence_v6.*` graph substrate is the nearest thing; objects and IDs are not unified                                            |
| 4 Products  | Exist, and read whatever they can find                                                | Tower reads a derived tree directly; this is a layer violation                                                                       |

### What layer confusion actually cost, this session

Each of these passed tests and passed source→mart reconciliation:

| Wrong output                                         | Layer violated                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| An airline reported as spending **$539.2M/yr on AI** | Classification inferred from a folder name instead of a field                                                       |
| Then reported as **$11.9M**                          | Same field still missing; the correction was another guess                                                          |
| **"Meridian has no IT budget"** — it is $650.0M      | One file read as the fact; no source-of-record declaration                                                          |
| **Lakeshore's budget** taken from the wrong company  | Identity inferred from a directory name; `lakeshore-holdings` and `lakeshore-industries` are two registered tenants |
| **$1,078.5M** where the figure was $539.2M           | A projection summed with another projection of the same money                                                       |

None of these were bugs in the ordinary sense. Every one was a layer boundary that existed in
someone's head and nowhere in the system.

## 9. How to use this document

Before you write code that touches tenant data, answer these in one line each:

1. **What layer am I working in?**
2. **What is the client responsible for here?**
3. **What does the adapter emit?**
4. **What is canonical?**
5. **What is deterministic, and what is generated?**
6. **What is the projection?**
7. **What owns the data?**
8. **What owns the presentation?**

If you cannot answer all eight, you are about to make a layer mistake. Stop and find out.

And before you state a Tower or tenant-intake headline metric: **run the lineage report in default
`quote` mode.** If the metric is `ONE_SOURCE`, say so when you quote it. If it is `CONFLICT`, do not
quote it until someone decides which source is authoritative and why.

For Source product/read-model numbers, run `node scripts/source/source-substrate-lineage-report.mjs`
and state the counting basis. Source portfolio value, contract count, vendor count, Contract 360
totals, optimization opportunity amount, evidence-readiness counts, finance-confirmed value,
Cube/consumption metrics, and other Source read-model values must be proved from the Source read
model, cube, opportunity spine, valuation ledger, or query with an explicit counting basis; the
Tower lineage report is not evidence for those Source projection figures. If a Source figure is
`ONE_SOURCE`, say so when you quote it. If it is `CONFLICT`, do not quote it until the owning read
model or calculation run is reconciled. If it is `ABSENT`, treat the number as unknown; missing is
not zero.
