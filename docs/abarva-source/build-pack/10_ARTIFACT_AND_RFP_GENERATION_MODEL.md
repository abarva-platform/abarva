# 10 ARTIFACT AND RFP GENERATION MODEL

## Purpose

AbarVa Source artifacts are governed work products, not disposable AI text.

Artifact generation must respect sourcing event state, required inputs, evidence, review status, approval routing, version history, and lock state. Nexus may assist with drafting, but Source owns the workflow state and artifact record.

## Artifact Families

Core artifact families:

- sourcing event brief
- minimum data request
- scope document
- sourcing strategy memo
- RFP/RFI package
- pricing template
- vendor Q&A tracker
- evaluation scorecard
- vendor exception log
- selection memo
- contract/mobilization checklist
- value ledger
- executive decision package

## Artifact Tiers

Artifact tier should reflect evidence and input completeness:

- Stub: structure exists, but required inputs are missing.
- Outline: major sections exist with assumptions clearly labeled.
- Rich: content is supported by required inputs, pattern guidance, and evidence/citations.

Nexus must not produce a Rich-tier artifact when required inputs are missing.

## Generation Rules

Nexus can assist with:

- structure
- section drafts
- executive summaries
- assumption labeling
- missing-input lists
- data request language
- review-ready narrative when evidence is available

Nexus cannot:

- invent client facts
- invent vendor facts
- invent pricing data
- bypass missing required inputs
- bypass scorecard lock rules
- bypass approvals
- mark an artifact issued without workflow state
- treat uploaded documents as trusted before parsing/validation

## Export / Edit / Re-Upload Model

Enterprise users will often edit artifacts outside Source. This is expected.

Source should support:

- export artifact to DOCX
- export pricing template to XLSX
- export scorecard to XLSX
- export executive package to PPTX or PDF later
- re-upload externally edited files
- classify uploaded file against expected artifact
- compare uploaded file to previous version
- extract change summary
- preserve reviewer/comment metadata when available
- preserve workflow state and audit trail

Source remains the system of record for:

- artifact identity
- artifact version
- workflow state
- review state
- approval state
- evidence/citation state
- lock state
- issue/publish state

## Artifact Versioning

Each artifact version should track:

- artifact id
- version id
- version number
- status
- owner
- created by
- modified by
- uploaded by if external
- source format
- generated by Nexus or uploaded by user
- source inputs used
- evidence/citations used
- change summary
- review state
- approval state
- lock state
- created timestamp
- modified timestamp

Versioning rules:

- exported artifacts keep a record of the exported version
- re-uploaded documents create a new artifact version
- locked artifacts cannot be edited in place
- reopening a locked artifact creates a new working version
- prior versions remain visible and auditable
- issued/published versions remain part of the event record

## Artifact Review Lifecycle

Artifact lifecycle:

1. Not Started
2. Draft
3. Needs Inputs
4. In Review
5. Changes Requested
6. Approved
7. Locked
8. Issued / Published
9. Superseded
10. Archived

Review behavior:

- comments attach to artifact version
- changes requested create a revision loop
- required comments must be resolved before lock
- approvals can be sequential or parallel
- approvals can expire or escalate
- waivers require rationale

## Locked And Reopened Behavior

Locked artifacts:

- cannot be edited in place
- can be exported
- can be issued/published
- can be superseded
- can be reopened only by authorized role

Reopened artifacts:

- create a new version
- record reason for reopen
- may require renewed approval
- preserve prior locked version

Material changes that should usually require re-approval:

- scope changes
- vendor list changes
- pricing template changes
- legal/security requirement changes
- scorecard weight changes
- selection recommendation changes
- value assumptions changes

## RFP/RFI Package Requirements

An RFP/RFI package should not be issued until:

- scope document is approved or waived
- RFP/RFI package is approved and locked
- pricing template is approved
- vendor list is approved
- scorecard is approved or at least governed according to event rigor
- legal/security/procurement approvals are complete when required
- release approval is complete
- audit record is generated

If required inputs are missing, Nexus may generate:

- missing input request
- outline/stub package
- assumption register
- readiness warning

Nexus must not silently generate a final release-ready RFP.

## Agent Responsibilities

Nexus:

- drafts artifacts within tier limits
- explains missing inputs
- recommends review and approval steps
- labels assumptions and confidence

Sentinel:

- validates evidence/citations
- flags unsupported claims
- checks uploaded/redlined files before they become trusted evidence

Atlas:

- prepares executive decision summaries from approved evidence
- summarizes approval status and unresolved risks

Steward:

- enforces lock, approval, waiver, and stage-gate rules
- prevents unsafe artifact state transitions
- logs audit events
