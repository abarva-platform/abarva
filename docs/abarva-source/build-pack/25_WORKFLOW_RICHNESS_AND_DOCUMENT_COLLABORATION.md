# 25 WORKFLOW RICHNESS AND DOCUMENT COLLABORATION

## Purpose

AbarVa Source must support real enterprise sourcing behavior, not a simple linear tracker or one-shot document generator.

Enterprise sourcing includes pauses, rework, offline edits, review cycles, approval routing, vendor response gaps, exceptions, audit evidence, and final decision packaging. Source must treat those behaviors as first-class workflow state.

Source is the system of intelligence, workflow, evidence, and state. Microsoft Office, Google Docs, email, and external collaboration channels may remain editing surfaces when needed. Source should coordinate them rather than pretend enterprise teams will edit every document in-app.

## Three Workflow Layers

### 1. Sourcing Event Workflow

This is the overall event-level flow:

1. Intake
2. Scope
3. Sourcing Strategy
4. RFP/RFI Package
5. Vendor Responses
6. Evaluation
7. Orals/BAFO
8. Selection
9. Contract/Mobilization
10. Value Realization

This layer answers:

- Where is the sourcing event?
- What stage is active?
- What is blocked, waiting, or ready?
- What artifacts are required for the next gate?
- What decisions or approvals are preventing movement?

### 2. Artifact Lifecycle Workflow

Every important artifact has its own lifecycle:

1. Not Started
2. Draft
3. Needs Inputs
4. In Review
5. Changes Requested
6. Approved
7. Locked
8. Issued / Published
9. Superseded
10. Archived

This applies to:

- scope document
- sourcing strategy memo
- RFP/RFI package
- pricing template
- vendor Q&A tracker
- scorecard
- selection memo
- mobilization checklist
- value ledger

This layer answers:

- What artifact exists?
- Which version is current?
- Is it draft, reviewed, approved, locked, issued, superseded, or archived?
- Who owns it?
- What inputs, evidence, approvals, or comments are still missing?

### 3. Review / Approval Workflow

Artifacts and stage movements require reviews and approvals that vary by event size, rigor, risk, and artifact type.

Core actions:

- request review
- assign reviewer
- set due date
- comment
- request revision
- approve
- reject
- resolve comments
- lock artifact

This layer answers:

- Who must review?
- Who must approve?
- Which approvals are sequential?
- Which approvals can happen in parallel?
- Is a waiver allowed?
- Is the stage gate blocked?

## Document Collaboration Requirements

Source must support document collaboration that fits enterprise sourcing reality.

Required capabilities:

- export artifact to DOCX
- export pricing template to XLSX
- export scorecard to XLSX
- export executive package to PPTX or PDF later
- allow external/offline edits
- allow re-upload of edited document
- classify re-uploaded document
- compare uploaded version to previous version
- extract change summary
- preserve version history
- preserve reviewer/comment metadata when available
- maintain Source as the system of record for workflow state

Offline and external edits are not failures. They are expected enterprise behavior.

Source should know:

- which artifact was exported
- who exported it
- which version was exported
- what format was exported
- when it was re-uploaded
- whether the re-upload matches the expected artifact
- what changed
- whether evidence/citation integrity still holds
- whether review or approval status must reset

## Artifact Versioning

Each artifact version should track:

- artifact id
- version id
- version number
- artifact type
- status
- owner
- created by
- modified by
- uploaded by if external
- source format
- generated by Nexus or uploaded by user
- source inputs used
- evidence/citations used
- change summary
- review state
- approval state
- lock state
- created timestamp
- modified timestamp
- issued/published timestamp when applicable

Example version chain:

- RFP Package v0.3 - Draft
- RFP Package v0.4 - Legal redlines uploaded
- RFP Package v0.5 - Procurement review complete
- RFP Package v1.0 - Approved for vendor release
- RFP Package v1.1 - Vendor Q&A addendum issued

Version rules:

- Re-uploaded external edits create a new version.
- Locked artifacts cannot be edited in place.
- Reopening a locked artifact creates a new working version.
- Superseded versions remain auditable.
- Issued/published artifacts remain visible even if a later version is drafted.

## Stage-Gate Artifact Requirements

Stage gates are not decorative. A stage cannot advance unless required artifacts and approvals are in the right state, or a waiver exists with rationale.

### Scope -> Sourcing Strategy

Required:

- scope document is Approved or explicitly waived
- required inputs are complete or waived
- major risks are reviewed
- Nexus readiness is above threshold
- value assumptions are directionally recorded

Blocked when:

- baseline data is missing
- retained responsibilities are unclear
- scope document is Needs Inputs
- risks are unreviewed
- readiness threshold is not met

### RFP/RFI Package -> Vendor Responses

Required:

- RFP/RFI package is Approved and Locked
- pricing template is Approved
- vendor list is Approved
- release approval is complete
- Q&A process owner is assigned

Blocked when:

- RFP package is still draft or in review
- pricing template is missing
- scorecard is not at least drafted
- legal/security/procurement approvals are incomplete when required
- vendor release list is not approved

### Evaluation -> Selection

Required:

- scorecard is Locked
- vendor responses are complete or exceptions are approved
- pricing is normalized or exceptions are documented
- decision memo is drafted
- risk and exception review is complete

Blocked when:

- scorecard weights are still editable
- vendor pricing templates are missing
- exceptions are not normalized
- qualitative scoring lacks rationale
- decision memo lacks evidence

## Wait States And Rework Loops

Source must support wait states and rework loops without losing control of the sourcing event.

Common wait states:

- waiting on client inputs
- waiting on vendor response
- waiting on procurement review
- waiting on legal review
- waiting on security review
- waiting on finance approval
- waiting on executive decision
- waiting on document redlines
- waiting on evidence/citation validation

Common rework loops:

- draft -> changes requested -> revised draft -> in review
- approved -> reopened -> new version -> approval required
- issued -> addendum needed -> new version -> reissue
- vendor response incomplete -> reminder -> exception review -> evaluation allowed or blocked

## Agent Responsibilities

Nexus:

- explains where the event is
- identifies missing artifacts, approvals, reviews, and inputs
- recommends next action
- labels what can be drafted, what must wait, and what cannot be trusted yet

Sentinel:

- validates evidence and citation integrity
- flags unsupported claims
- checks uploaded/redlined documents before they are trusted

Atlas:

- summarizes review/approval posture for executives
- prepares decision-package narratives from approved evidence only

Steward:

- enforces stage gates
- prevents unsafe workflow movement
- requires waiver rationale when exceptions are allowed
- logs audit-relevant workflow events

## Audit Trail Requirements

Every material workflow event should be audit-visible:

- artifact generated
- artifact exported
- artifact uploaded
- version created
- review requested
- comment added
- change requested
- approval granted
- approval rejected
- waiver applied
- artifact locked
- artifact issued
- stage advanced
- gate blocked
- gate reopened

Audit records should include:

- actor
- role
- timestamp
- event id
- artifact id/version id when applicable
- action
- rationale
- source evidence or citation references where applicable

## Product Boundary

Do not build this workflow richness as a vendor portal first.

Do not implement full document editing in-app before export/import/versioning and review state are defined.

Do not allow model-generated document language to bypass workflow gates, approvals, evidence, or artifact version rules.
