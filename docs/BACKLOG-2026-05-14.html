Workstream A

Engineering

Highest leverage. Two items already partially shipped from the 2026-05-13 audit arc. A1 (end-to-end testing) is the single largest unlock — every pilot-ops claim downstream depends on it.

ID Item Scope Assumptions Solution Desired outcomes
A1 End-to-end testing coverageTop priority Login → Home → Intelligence → Source → Strategic Moves → Tower, per tenant. The 8 SEC-P0 cross-tenant probes from the 2026-05-13 audit B-agent become a permanent regression suite. Playwright is the runner of choice. Tests run on a prod-like staging environment with seeded fixtures, not on prod. Cross-tenant curl probes are a separate fast suite that does not require a browser. Two suites: (1) Playwright per-tenant smoke for every primary surface, nightly + on-PR. (2) curl-based SEC-P0 regression that asserts 403 forbidden_cross_tenant on the 8 routes. Both land in CI before any pilot conversation. Every primary CXO flow has an automated smoke. Cross-tenant 403s catch regressions before customers see them. A1 is the precondition stated in C1, C2, C3.
A2 Context layer stand-up + refreshPartial · in flight One-command bootstrap to add a new tenant. Refresh-from-upstream doctrine: how a customer pulls a fresh industry corpus and applies tenant overrides on top. The 14-segment setup data structure proven by the First Capital pack (PR #1929) is canonical. Tenant onboarding is opinionated, not bespoke per customer. Two scripts. npm run tenant:bootstrap <key> provisions Clerk + Supabase + seed pack + JWT pin. npm run tenant:refresh re-pulls the industry corpus and rebuilds intelligence chunks while preserving tenant-specific overlays. A 4th tenant can be onboarded in under an hour without engineering hand-holding. Refresh is push-button. Documented in a single README.
A3 Platform vs tenant feature gatingPartial · in flight Explicit contract for what ships to all tenants vs what is pinned per client. Server-side and client-side enforcement. Most features are platform-wide; tenant-specific is the exception, not the norm. We won’t ship many tenant-only features early. A features.ts registry + a useFeature(name) hook + a server-side isFeatureEnabled(ctx, name). Default off for tenant-specific, default on for platform. Reuses the locked-role pinning resolver from PR #1930. A new tenant cannot accidentally see a half-shipped feature. Rolling a feature to one pilot tenant first is one config change, not a code branch.
Workstream B

Azure infrastructure

Five items, mostly research → design docs. Can run fully parallel to engineering. B1 → B2 is the one internal sequence; everything else is independent. B5 is the unlock for any infosec conversation (C4).

ID Item Scope Assumptions Solution Desired outcomes
B1 SaaS architecture decisionOpen Three-tier segregation: (a) application tier (b) per-client data plane (c) industry corpus / shared substrate. Identity boundary between them. Network topology. Azure is the primary cloud. Supabase either remains as the data plane or migrates to Azure Postgres in a follow-on cycle. Pinecone / Neo4j either stay or get replaced by Azure-native options. A 6-page design doc with diagrams. App tier on Azure App Service (or Vercel until migration) → broker contract → client data plane (per-tenant Postgres schema for pilots, dedicated DB for production) → shared read-only industry corpus. Identity via Entra ID + Clerk passthrough. A customer’s security architect can read this doc and respond “yes, our data is isolated.” Document is also the seed for the infosec accelerator (C4).
B2 Demo private planes (3 tenants)Open Reference deployment of B1 for Apex / Meridian / First Capital. Demonstrable to a customer’s sec team without showing real customer data. Cost-effective at demo scale (≤ $500/mo total). Tear-down and recreate in under a day. No real PHI/PII; the dummy data is the proof. Bicep or Terraform modules per tenant. CI pipeline deploys all three on demand. URLs published internally with read-only sec-team access. Three live URLs proving segregation. A reusable artifact for every infosec review, every investor demo, every internal architecture conversation.
B3 SaaS vs corporate Azure setupOpen Landing zone yes/no. Subscription model (per-environment vs per-customer). Network topology. Identity boundary. Azure for Startups gets approved (D5). We are building for hundreds of tenants in the medium term, not thousands today. Single Azure tenant. Subscription-per-environment (dev / staging / prod). Landing zone deferred until the first enterprise customer asks for one. ADR documents the deferral. Decision recorded. Not over-engineered for current scale. Clear upgrade path to landing zone when an enterprise customer signs.
B4 Client VPC deploymentOpen Lift-and-shift of the AbarVa stack into a customer’s Azure subscription. One-time setup cost. Ongoing maintenance cost. Control-plane boundary. Customer provides the Azure landing zone. We provide Bicep / Terraform. Maintenance is shared: customer owns infra, we own application. Opinionated Bicep modules with a parameter file per customer. AbarVa retains app-tier control via Entra-ID-federated service principal in the customer’s subscription. Cost model: setup ≤ 5 business days + 4-8 hrs/mo maintenance. A repeatable VPC deployment SKU we can quote on. The biggest infosec unlock per C4. Lowest-friction path for regulated customers.
B5 PHI / PII preventionOpen · gates C4 Ingest-time filtering on tenant uploads. Explicit boundary: what is the client context layer allowed to hold by design? What enforces the boundary if a user uploads sensitive data by mistake? AbarVa does NOT need PHI or PII to ground the product. If sensitive data shows up, it is a mistake. Rejection at ingest is the right answer, not redaction-and-store. Microsoft Purview content scan on every upload before write to data plane. Reject if PHI/PII detected. Surface to user: “we don’t accept this data.” Audit log every rejection. Tenancy guards from PR #1923 are the foundation. Zero PHI/PII in any client context layer by construction. Sec teams accept this as a HIPAA-friendly / GDPR-friendly story. Becomes a positive selling point.
Workstream C

Pilot operations

Planning can start now; execution depends on the A and B baselines. C4 is the highest-leverage standalone item — it’s the unlock for every signed pilot.

ID Item Scope Assumptions Solution Desired outcomes
C1 First-pilot deployment runbookOpen · depends on A+B Step-by-step from “signed SOW” to “first CXO logged in.” Legal, infosec, technical, training. A1 (E2E coverage) and B-cluster baseline are done. Customer either uses the AbarVa SaaS plane or their own Azure subscription per B4. A sequenced checklist with owner + ETA per step. Three swimlanes: legal/contractual, technical/deployment, customer-facing training. Lives in a single Notion / repo doc. Pilot kickoff in ≤ 2 weeks from SOW. Repeatable; customer #2 onboards faster than customer #1.
C2 Support modelOpen Minimum viable support shape for a pilot customer. What team, what hours, what SLA we can commit to without burning out a 1-2 person company. Founder-led. Pilot count < 5. SLAs reasonable (24h response, no 24/7 paging yet). Founder is primary on-call. Contracted SRE on retainer for after-hours. One DPA / sec analyst contracted for customer audits as need arises. No full-time hires before second paid pilot. First pilot serviced without hiring a 5-person ops team. Cost of support is predictable and bounded.
C3 Sustaining pilotOpen Pager rotation, escalation policy, post-incident reviews, SLA we publicly commit to. Same as C2 — founder-led, contracted SRE. SOC 2 not yet, but observability and audit log are in place. PagerDuty (or similar) routing to founder + SRE. Escalation matrix. Documented post-incident review template. SLA: 99.5% availability initially. No customer-visible downtime during pilot. Clear PIRs published to customer within 24h of any P1 incident.
C4 Infosec approval acceleratorGating for any signed pilot The single biggest pilot blocker. Output: a checklist of features and controls that unlocks corporate security review. Pre-filled CAIQ / SIG-lite. Client VPC deployment is the biggest unlock. SOC 2 is not done, but we have a credible roadmap. PHI/PII rejection (B5) is the second-biggest unlock. A two-page exec summary + a pre-filled standard CAIQ. Named features: client VPC available (B4), RBAC, audit log, RLS, broker boundary, PHI/PII guardrails (B5), tenancy isolation (PR #1923). Backed by an SOC 2 readiness statement. A customer’s security architect can review and approve in ≤ 2 weeks. Conversion rate on signed-LOI → in-production pilot rises sharply.
Workstream D

Business / GTM

Fully independent of engineering — different humans entirely. D1 (narrative) is the gating dependency for D2 and D6 and informs C4. D5 (startup credits) is the lowest-effort highest-upside item in the whole backlog.

ID Item Scope Assumptions Solution Desired outcomes
D1 Product narrative + value propositionGating One-pager + 3-slide deck. The phrasing that everyone — founder, advisor, sales, investor — uses verbatim. Audience is the business CXO (CEO / CFO / COO), not tech-only. Positioning is “tenant-grounded consultant-grade decision OS for C-suite AI and business bets.” AbarVa is not another LLM wrapper. Founder + advisor session. Iterate against three real CXO conversations. Lock the language. Bake into every surface (sign-in, marketing site, deck, README). A CXO can repeat the value prop back after one read. Team uses identical phrasing everywhere. D2 and D6 inherit it cleanly.
D2 MonetizationOpen · depends on D1 Tier structure + ARR model. Per-tenant vs per-seat vs platform license. What’s included per tier. Per-tenant licensing given CXO concentration. Pilot pricing distinct from production. ARR target plausible in year 1. Three tiers — Pilot ($50–$100k, 6-mo) → Production ($250–$500k/yr) → Enterprise ($1M+ with VPC deployment). Inclusion matrix per tier. Sales conversations have a price anchor. ARR target line-of-sight for the seed pitch (D6).
D3 Patent decisionQuick win · decision File a provisional, file a defensive publication, or pass. A decision, not a project. Most of AbarVa is software composition; the broker contract + tenancy isolation + tenant-grounded reasoning architecture may have unique angles. Provisional ~$3–5k, full ~$15–25k, defensive publication near-free. 1-hour call with a patent attorney. ADR records the decision and reasoning. Decision made. Either provisional filed (12-month runway) or moved on.
D4 Company setup costOpen Foundational registration + legal + insurance + bookkeeping for the first 3–6 months. Delaware C-corp. First pilot in scope. Team of 1–2 founders. E&O + cyber insurance ($3–8k/yr). Bookkeeping ($300–500/mo). Total 3–6 mo: $10–25k. Cost projected and reserved for in the seed ask. No surprises before first signed pilot.

Anthropic ~$5k–$25k. Each application is a 1–2 hour form. Founder fills both applications in one sitting. Existing AbarVa narrative (D1) + this backlog is the supporting material. $30k+ in credits secured. Pilot-phase infra cost goes to near-zero. Marginal cost-per-tenant during pilots becomes negligible.
D6 Seed funding planOpen · depends on D1, D2 Thesis, ask, use of proceeds, intent. Investor list. Deck + memo. D1 + D2 are locked. Pre-seed / seed amount in the $1–3M range. Lead investor with relevant AI / enterprise SaaS thesis. 10-slide deck + 1-page memo. Use of proceeds split (people / infra / sales). Targeted outreach to 15–25 investors, not a broad spray. Term sheet within 90 days of starting the raise. Sufficient runway for 18 months and a second paid pilot.
