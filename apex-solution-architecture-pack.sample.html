Section 1 · Architecture decision

Shape the Move around a broker-mediated human-in-the-loop agent — not a read-only copilot, and not full autonomy.

Target-state architecture pattern
Broker-mediated, retrieval-grounded human-in-the-loop agent

An agent grounded by broker-scoped retrieval over the tenant context layer that proposes and prepares the routing action, then executes only after a named human approves it — agent-assist over the system-of-record, with human-in-the-loop as the control.

Patterns considered and rejected, and the decision rationale
Read-only retrieval copilot Rejected
A read-only assistant under-shapes the Move — routing needs an agent that prepares the routing action, not one that only answers questions about it.
Full autonomous agentic workflow Rejected
Full autonomy is rejected: the scenario evidence requires a named human accountable before autonomy expands, and intent data is still fragmented (the CDP gap). Premature for release 1.
Decision rationale
  • Shaped around the recommended archetype "Human-in-the-Loop Agent" from the suitability assessment.
  • "Full agentic workflow" covers all eight §4 reference-architecture components natively — it is shaped as a product, not a POC.
  • Scenario guardrail overrides ambition: Brokered human-in-the-loop agent is selected because the tenant evidence requires human accountability before autonomy expands.
So whatThe architecture is selected; the agent boundary, the human checkpoint and the broker contract are the design every later section builds on.
Decision roleDecide which target-state architecture pattern to fund and shape the delivery boundary around.
